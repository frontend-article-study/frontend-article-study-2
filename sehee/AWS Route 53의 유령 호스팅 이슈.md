# AWS Route 53의 유령 호스팅 이슈

회사에서 더 이상 업데이트하지 않는 레거시 게임서버측의 동작을 확인할 일이 있어서, 코드를 보는 김에 이 서버가 어떤 클라우드플랫폼의 어떤 서비스에 올려져 있는가를 찾아봤다.

그런데 구서버 API URL 도메인의 AWS Route53 호스팅 영역을 보니, 아무 곳에도 연결이 되지 않고 있었다.

<img width="1245" height="703" alt="image" src="https://github.com/user-attachments/assets/0bf3bc5d-9c89-4e81-9285-d21c89e36ea8" />


오직 이 두 레코드 뿐이었는데, 실질적으로 이 도메인이 어딘가에 연결이 되어있으려면 A, AAAA, CNAME 등 외부자원을 나타내는 유형의 레코드가 있어야 한다.

그러면 서버 요청이 허공으로만 전해지고 동작하지 않고 있는가하면 그것도 아니고 이 서버는 동작이 너무 잘 되고 있었다.

이 미스터리를 푸는 데 많은 시간이 걸렸다. 결론적으로는 도메인 시스템에 대한 이해가 미숙해서 대시보드를 잘못 둘러봐서 생긴 일이었다.

이번 기회에 도메인 시스템과 Route 53에 관해 공부했던 것들을 정리해보았다.

## 도메인 관련 키워드

Route 53 대시보드를 보면 생소한 용어들이 있다. 호스팅 영역, 레코드, 네임서버…

이것을 알지 않으면 Route 53의 도메인이 어떻게 실서버와 연결되는지 알기가 어렵다.

### 도메인 등록기관(Registrar)

도메인을 산 곳. ICANN 인증을 받아 특정 TLD의 도메인 등록을 처리하는 회사이다.

흔히 가비아, 후이즈, GoDaddy 등을 도메인 등록기관으로 볼 수 있다.

Route 53에서도 도메인 구매 및 관리 서비스를 제공하며, 이는 Route 53 > 등록된 도메인 섹션에서 확인할 수 있다.

### 네임서버(Name Server)

도메인의 DNS 설정을 실제로 관리하는 서버이다.

엄밀히 말하면 네임서버에는 루트 네임 서버, TLD 네임 서버 등 여러 종류가 있지만, 일반적으로 네임서버라고 하면 Authoritative Name Server, 즉 **특정 도메인의 DNS 레코드를 실질적으로 갖고 있는 최종 네임서버**를 말한다.

한마디로 도메인 이름과 IP 주소를 연결해주는 서버라고 생각하면 된다.

네임서버는 도메인 등록기관과 다를 수 있다. 예를 들면 도메인을 AWS에서 샀어도 네임서버를 Cloudflare나 GCP 쪽으로 바꿀 수 있다.

### DNS 레코드(Record)

DNS 서버에 저장되는 실제 연결 규칙이다. 후술할 호스팅 영역(hosted zone) 안에서 도메인이나 서브도메인을 어디로 보낼지 정의하는 객체라고 할 수 있다.

DNS 서버는 내부적으로 이런 정보들을 여러 줄 들고 있는데,

```
www.example.com -> ELB로 보내라
_live.example.com -> 이 EC2 주소를 가리켜라
example.com -> 이 도메인의 네임서버는 AWS다
```

이 한 줄 한 줄을 **레코드**라고 한다.

### 레코드의 구성

보통 레코드는 이런 요소로 이루어진다.

- 이름 : 어떤 도메인/서브도메인에 대한 정보인지
- 유형 : 무슨 종류의 정보인지(ex: A, CNAME, NS, SOA)
- 값 : 실제로 가리키는 대상이 뭔지
- TTL : DNS 캐시를 얼마나 오래 갖고 있을지

ex)

```
이름: www.example.com
유형: CNAME
값: example-elb.amazonaws.com
```

(실제로 이렇게 저장되진 않는다. 의미론적으로 이렇다는 것)

### 한 도메인에 여러 레코드가 있는 이유

예를 들어 `example.com`이라는 도메인에 대해 DNS는 여러 종류의 질문을 받을 수 있다.

- 이 도메인의 네임서버가 뭐냐?
- 이 도메인의 기본 설정이 뭐냐?
- `www.example.com`은 어디로 가냐?
- `api.example.com`은 어디로 가냐?
- IPv4는 뭐냐?
- IPv6는 뭐냐?

이 질문들이 다르니 레코드도 여러 개가 생긴다.

서브도메인별로 각각 다른 레코드를 갖는 것은 정상이며, 같은 이름 `www.example.com`에 연결된 IPv4 주소와 IPv6 주소가 둘 다 있을 수도 있다. 혹은 같은 이름에 여러 IPv4 주소가 있을 수도 있다.

> 
> 
> 
> **서브도메인이란**
> 
> 도메인은 오른쪽에서 왼쪽으로 갈수록 좁아지는 계층 구조이다. `com`이 최상위 도메인(TLD)이고, 그 아래에 `example.com`이 있고, 다시 그 아래에 `www.example.com`이 있는 식이다.
> 이때 **상위 도메인 아래에 딸린 하위 영역**이 서브도메인이다. 즉 `www.example.com`은 `example.com`의 서브도메인이다.
> DNS 입장에서 각 서브도메인은 별개의 이름이고, 따라서 각각 별도의 레코드를 가져야 한다. (루트 도메인의 레코드는 상속되지 않는다.)
> 예를 들어 `example.com`에 A 레코드를 걸어놨어도 `www.example.com`이 자동으로 같은 곳을 가리키지 않는다.
> 

### 레코드 타입

레코드 타입에는 대표적으로 다음과 같은 것들이 있다.

| 타입 | 의미 | 예시 값 |
| --- | --- | --- |
| A | 도메인을 IPv4 주소로 연결 | 3.36.xxx.255 |
| AAAA | 도메인을 IPv6 주소로 연결 | 2406:da00:ff00::… |
| CNAME | 다른 도메인 이름으로 연결(이 도메인은 다른 도메인을 가리킨다)<br></br>같은 이름에 CNAME 레코드가 있으면 A 레코드 같은 다른 레코드를 함께 둘 수 없다. CNAME은 "이 이름은 다른 이름의 별칭이니 그쪽에 물어보라"는 선언이라, 같은 자리에 또 다른 답이 있으면 모순이 되기 때문이다. | ec2-13-xxx.compute.amazonaws.com |
| MX | 메일 서버 지정 | mail.example.com |
| NS | 이 도메인을 담당하는 네임서버(이 도메인을 관리하는 DNS 서버는 여기다 라는 의미)<br></br>루트 도메인(`example.com`)에는 SOA·NS 레코드가 필수로 존재해야 한다. | ns-123.awsdns-xx.net |
| SOA | DNS 영역의 기본 정보. 내부 관리용 정보<br></br>루트 도메인(`example.com`)에는 SOA·NS 레코드가 필수로 존재해야 한다. |  |
| TXT | 인증용 텍스트 값 |  |

이 중 실질적으로 도메인을 외부 자원으로 연결하는 타입은 A, AAAA, CNAME, MX라고 할 수 있다.

그래서 처음 우리 구서버 이미지를 봤을 때, 이 서버에 연결된 리소스가 없네? 하고 미스터리에 빠졌던 것이다.

### 호스팅 영역(Hosted Zone)

도메인의 DNS 레코드들을 담는 설정 파일 같은 컨테이너이다.

레코드가 앞서 말했듯 도메인과 그 하위 도메인의 트래픽 라우팅 정보를 담는 규칙이라면, 이 레코드들이 담긴 컨테이너를 호스팅 영역이라고 한다.

ex) example.com hosted zone은 다음과 같이 생겼다.

```
Hosted Zone: example.com

A record
example.com → 1.2.3.4

CNAME record
www.example.com → example.com

MX record
example.com → mail server

TXT record
example.com → 인증용 값
```

즉 호스팅 영역이 있다는 건 해당 도메인의 DNS 설정파일이 있다는 의미다.

그러나 **Hosted Zone이 있다고 해서 무조건 실제로 사용 중인 DNS는 아니다.**

Hosted Zone과 Record를 아무리 잘 세팅해놔도, **도메인 등록기관 쪽에서 해당 Route 53 네임서버를 도메인의 네임서버로 지정해두지 않으면 그 설정은 실제로 쓰이지 않는다.**

## 그래서 유령 호스팅은 무엇이었나

지금까지의 정보를 바탕으로 도메인 연결 흐름을 정리해보면 다음과 같다.

예를 들어 example.com을 Route 53를 통해 AWS ALB로 연결한다고 하면,

```
1. 도메인을 구매한다.
   예: 가비아에서 example.com 구매

2. Route 53에 Hosted Zone을 만든다.
   Hosted Zone: example.com

3. 2번을 완료하면 Route 53이 NS 4개를 발급한다.
   예:
   ns-123.awsdns-xx.com
   ns-456.awsdns-xx.net
   ns-789.awsdns-xx.org
   ns-000.awsdns-xx.co.uk

4. 도메인 등록기관의 도메인 관리 화면에서 기존 네임서버 값을 제거하고 위 3번에서 발급된 네임서버를 등록한다.

5. Route 53 Hosted Zone 안에 Record를 만든다.
   A Alias:
   example.com → AWS ALB
   
6. 이러면 사용자는 다음 흐름으로 접속이 됨
	 1) 사용자가 example.com 접속
	 2) DNS가 Route 53에 물어보고 ALB 주소를 받음
	 3) 브라우저가 ALB로 접속	 
```

이런 흐름이 된다.

이 때 중요한 것은 4번, **도메인 등록기관의 도메인 관리 화면에서 네임서버를 위 Route 53에서 발급된 NS로 바꿔야 호스팅 영역에서 세팅해뒀던 레코드들이 작동한다는 것이다.**

Route 53 대시보드를 보면 UI가 이렇다.

<img width="2470" height="874" alt="image" src="https://github.com/user-attachments/assets/424ea88f-f4b5-48dd-a527-6b759cd1acb9" />


흔히 Route 53 관리를 한다하면 아무 생각 없이 저 호스팅 영역 부분을 누르게 된다. 사이드바 맨 상단에 위치해있고, 대시보드에서도 가장 잘 보이는 좌측 상단에 있으니까.

Route 53을 통해 도메인 이름을 등록하면(도메인을 구매하면) 도메인과 동일한 이름의 공용 호스팅 영역이 자동으로 생성되며 네임서버가 할당되고, 해당 도메인과 네임서버가 연결된다.

실질적으로 라우팅 관리를 할 때 자주 볼 페이지는 도메인 정보 페이지가 아니라 레코드 설정 페이지일 것이므로 이 UI는 어찌보면 자연스러운 흐름이다.

그러나 만약 Route 53에서 구매한 도메인에 다른 네임서버를 등록한 경우라면?

도메인 구입 시 자동생성된 호스팅 영역은 그대로 남고, 어쩌면 레코드도 연결된 채 남아있다. 하지만 실제 도메인 라우팅 양상은 해당 설정값대로 동작하지 않는다.

이게 우리 상황이었다.

Route 53에서 구매한 도메인의 네임서버 연결 상황은 **Route 53 > 등록된 도메인** 섹션에서 확인할 수 있다.

<img width="2076" height="352" alt="image" src="https://github.com/user-attachments/assets/4f82ea8c-42d4-42ae-84d6-1bca8631d1c0" />


확인해본 결과, **우리 도메인에 실질적으로 연결된 네임서버는 클라우드플레어에 있었다.**

호스팅 영역 데이터는 실제로 사용되지 않는 찌꺼기였던 것이다.

이 정보를 바탕으로 클라우드플레어의 DNS 대시보드에 가니… 실질 자원과 연결된 A, AAAA 레코드를 확인할 수 있었고, 비로소 우리 구서버가 GCP App Engine에 연결되어 있다는 사실을 찾을 수 있었다.

AWS Route 53 UI가 의미하는 것들이 명확하지 않아서 생긴 해프닝이었다.
