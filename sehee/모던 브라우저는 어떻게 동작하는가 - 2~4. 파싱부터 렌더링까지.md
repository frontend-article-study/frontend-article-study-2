### HTML 파싱과 DOM 생성

- 렌더러의 메인 스레드가 HTML 명세에 따라 파싱해 **DOM** 트리를 만든다.
- **스트리밍 방식** : HTML 파일 전체를 다 받기 전에도 들어온 만큼 DOM을 만들기 시작한다.
- **오류에 관대(error-tolerant)** : 마크업이 아무리 엉망이어도 명세상 반드시 DOM을 만들어낸다.
    - ex) `<p>Hello <div>World</div>` ⇒ `<div>` 앞에서 `<p>`를 자동으로 닫는다.
- 파싱 중 `<link rel="stylesheet">`, `<img src>`를 만나면 네트워크에 요청을 보내고 파싱은 계속 진행한다. **스크립트 태그는 예외로 파싱을 멈춘다**.

### `<script>`는 왜 파싱을 멈추는가

- 기본 `<script>`를 만나면 파서는 멈추고, 스크립트를 다운로드·실행한 뒤에야 파싱을 재개한다.
- 이유 : 스크립트가 `document.write()` 등으로 아직 파싱되지 않은 페이지 구조를 바꿀 수 있기 때문. 실행 순서를 HTML 순서와 맞추려면 그 자리에서 실행해야 한다.
    - ⇒ `<head>`에 큰 스크립트를 넣으면 렌더링이 늦어지는 이유
- `async`, `defer`, `type="module"`로 이 동작을 바꿀 수 있다.

| 방식 | 다운로드 | 실행 시점 | 실행 순서 보장 |
| --- | --- | --- | --- |
| 기본 `<script>` | 파싱 멈추고 다운로드 | 다운로드가 끝난 후 즉시 | O |
| `async` | 파싱과 병렬 | 다운로드가 끝난 후 즉시
 | X (작은 파일이 먼저 받아지면 먼저 실행) |
| `defer` | 파싱과 병렬 | HTML 파싱 완료 후 | O (태그가 호출된 순서대로) |
| `type="module"` | 파싱과 병렬 | 기본적으로 defer처럼 동작 | O |
- `async`는 다운로드가 병렬일 뿐, **실행하는 순간에는 여전히 파서가 멈춘다.** 실행 순서가 중요하거나 DOM이 필요한 스크립트라면 `defer`가 더 안전하다.

### CSS 파싱과 CSSOM, 스타일 계산

- CSS 파일과 `<style>` 블록을 파싱해 규칙 목록인 **CSSOM**을 만든다.
- **스타일 계산(style resolution)** : DOM과 CSSOM을 합쳐 각 요소에 어떤 규칙이 적용되는지 정하고, 캐스케이드·상속·기본값을 반영한 최종 **computed style**을 계산한다.
- 작성자 CSS가 없어도 **user-agent 스타일시트**(브라우저 기본 스타일)가 가장 낮은 우선순위로 적용된다. ex) `<h1>`의 기본 font-size, margin
- DevTools의 Computed 탭에서 요소의 최종 스타일을 확인할 수 있다.

### 렌더 블로킹

- HTML 파싱은 CSS 없이도 진행되지만, **첫 렌더는 `<head>`의 CSS가 로드될 때까지 기다린다.** 불완전한 스타일로 그리면 스타일 없는 화면이 번쩍이기(FOUC) 때문.
    - 파싱 : HTML 텍스트를 읽어서 DOM 트리를 만든 상태. 메모리 안에 구조만 생겼고 아직 화면에는 아무것도 안 나온 상태
    - 렌더 : DOM에 스타일을 입히고(스타일 계산), 위치·크기를 정하고(레이아웃), 실제 픽셀로 그리는(페인트) 과정 전체. 렌더가 끝나야 화면에 보임
- CSS가 준비되면 브라우저는 지금까지 파싱된 부분부터 먼저 그린다. (파싱과 렌더는 따로 돌면서 맞물려 진행)
- `async`/`defer`가 없는 `<script>`가 CSS `<link>` 뒤에 있으면, 스크립트는 **CSS 로드까지 기다렸다가** 실행된다. 스크립트가 DOM API로 스타일 정보를 읽을 수 있기 때문.
    
    ```html
    <head>
      <link rel="stylesheet" href="style.css">  <!-- .box { width: 300px } 가 들어 있음 -->
      <script>
        const box = document.querySelector('.box');
        console.log(getComputedStyle(document.body).margin); // 스타일 값을 읽음
      </script>
    </head>
    ```
    
- 실무 팁 : 스타일시트는 `<head>`에(CSS는 어차피 렌더를 막기 때문에 맨 위에 둬서 최대한 일찍 다운로드), 크거나 덜 중요한 스크립트는 `defer`/`async` 를 붙이거나 문서 하단에 두면 렌더 블로킹을 막을 수 있음

## 3. 스타일과 레이아웃

- 레이아웃 : 각 요소가 **화면 어디에, 얼마만 한 크기로** 놓이는지 계산하는 단계. 박스 모델, 일반 흐름, flexbox, grid 등 CSS 명세의 알고리즘을 따른다.
- 변경 때문에 다시 계산하는 것을 리플로우(reflow)라고 부른다.

### 레이아웃 트리

|  | DOM | 레이아웃 트리 |
| --- | --- | --- |
| 만드는 재료 | HTML | DOM + computed style |
| 담는 것 | 문서의 모든 노드 (보이든 말든) | 화면에 박스로 그려질 것만 |
| 갖는 정보 | 태그, 속성, 텍스트, 부모·자식 관계 | 각 박스의 위치(x, y)와 크기(width, height) |
| JS에서 접근 | `document.querySelector` 등으로 직접 접근 | 직접은 못 봄. `getBoundingClientRect()`로 결과값만 조회 |
- DOM을 순회하며 **레이아웃 트리**(render tree, frame tree)를 만든다. 레이아웃 트리의 구조는 DOM과 비슷하지만 차이가 있다.
    - `display: none` 요소는 **아예 빠진다.** 반면 `visibility: hidden`은 박스가 생기고 공간도 차지하며, 그리지만 않는다.
    - `::before`, `::after`처럼 CSS로 만든 가짜 요소는 DOM에는 없지만 레이아웃 트리에는 포함된다.
    - `<script>`, `<meta>`처럼 보이지 않는 요소는 레이아웃 트리에서 빠진다.
    - 여러 줄에 걸친 인라인 요소는 레이아웃 트리 내에서 여러 박스로 쪼개지기도 한다.

### 레이아웃은 비싸다

- 요소의 위치(x, y)와 크기(width, height)는 부모와 자식이 서로 값을 주고받으면서 **루트부터 재귀적으로 계산**된다.
    
    ```
    <html> 너비 1000px
     └ <body> → "부모가 1000px이니 나는 margin 빼고 984px"
        └ <div> → "부모가 984px이니 나도 984px"
           └ <p> 텍스트 → "984px 폭에 글자 넣어보니 3줄 → 높이 72px"
        ← <div> 높이 = 자식들 높이 합
     ← <body> 높이 = ...
    ```
    
    - 너비는 위에서 아래로 : 부모 너비가 정해져야 자식이 쓸 수 있는 폭이 정해진다.
    - 높이는 아래에서 위로 : 자식 내용이 다 들어가봐야 부모 높이가 정해진다.
    
    ⇒ 트리를 맨 위부터 내려갔다가 다시 올라오며 계산한다. (재귀적 계산)
    
- 단순한 배치의 경우에도 계산에 적용되는 특이사항이 많아 복잡하다.
    - **텍스트 줄바꿈** : 글자가 한 줄에 몇 개 들어가는지는 폰트를 실제로 측정해봐야 알 수 있다. (폰트가 바뀌면 줄 수가 바뀌고, 줄 수가 바뀌면 높이가 바뀜)
    - **margin collapsing** : 위 요소 `margin-bottom: 20px`, 아래 요소 `margin-top: 30px`이면 간격이 50px이 아니라 **30px**으로 적용된다. (세로 margin은 겹쳐서 큰 쪽만 남음)
    - **float** : 이미지에 `float: left`를 주면 글자가 그 옆으로 흐르는데, 이 경우 다른 요소들의 줄 폭이 float 때문에 달라진다.
    - **absolute** : `position: absolute`는 흐름에서 빠져서, 다른 요소 자리를 차지하지 않고 기준 조상 기준으로 따로 배치된다.
- JS가 요소 크기를 바꾸거나 콘텐츠를 추가하면 페이지 일부 또는 전체를 다시 레이아웃해야 한다.
- 브라우저는 바뀐("dirty") 부분만 다시 계산하려 하지만, DOM 상위에서 바뀌면 큰 페이지 전체를 다시 계산해야 할 수도 있다.
    
    ex) `body`의 `font-size`가 바뀜 ⇒ 모든 글자 크기가 바뀌니까 페이지 전체를 다시 계산해야 함
    
- **레이아웃 스래싱(layout thrashing)**
    - 브라우저는 레이아웃을 게으르게 처리함
        - 스타일을 바꾸면 바로 계산하지 않고 "다시 계산 필요(dirty)" 표시만 해둠
        - 다음 프레임을 그리기 직전에 모아서 한 번만 계산
    - 그런데 레이아웃 값을 읽는 순간 미뤄둔 계산을 즉시 해야 함 ⇒ 강제 동기 레이아웃(forced synchronous layout)
        - 레이아웃을 강제하는 읽기 : `offsetWidth/Height`, `clientWidth`, `scrollTop`, `getBoundingClientRect()`, `getComputedStyle()` 등
    - 스래싱 : 쓰기 → 읽기를 루프에서 반복해서, 한 번이면 될 레이아웃이 반복 횟수만큼 일어나는 것
    - 해결 : **읽기는 먼저 모으고, 쓰기는 나중에 한 번에 하기**
        
        ```jsx
        // ❌ 읽기 → 쓰기를 반복: 매 반복마다 강제 동기 레이아웃 발생
        for (const item of items) {
          item.style.width = container.offsetWidth + 'px'; // offsetWidth 읽기가 레이아웃 강제
        }
        
        // ✅ 읽기를 먼저 모으고, 쓰기는 한 번에
        const width = container.offsetWidth; // 레이아웃 1번
        for (const item of items) {
          item.style.width = width + 'px';
        }
        ```
        
        - 쓰기를 `requestAnimationFrame` 안으로 미루는 것도 방법
    - 확인 : DevTools Performance 탭에서 보라색 Layout 막대에 **Forced reflow** 경고가 뜨는지 보면 됨

## 4. 페인트, 컴포지팅, GPU 렌더링

### 페인트 = 뭘 어떤 순서로 그릴지 명령 목록 만들기

- 페인트 단계에서 화면에 픽셀을 찍지는 않으며, **무엇을 어디에 어떤 순서로 그릴지 적은 명령 목록**인 **paint record(display list)**를 만드는 단계다. (실제 픽셀로 바꾸는 건 다음 단계인 래스터)
- 레이아웃 후 메인 스레드가 레이아웃 트리를 순회하며 박스마다 그리기 명령을 기록한다.

```html
<style>
  body { margin: 0; }
  .card { position: absolute; left: 20px; top: 20px; width: 300px; height: 120px;
          background: #fff; border: 1px solid #ddd; }
  .btn  { position: absolute; left: 20px; top: 30px; width: 80px; height: 36px;
          background: #2563eb; color: #fff; border: 0; border-radius: 6px; font-size: 16px; }
</style>
<div class="card"><button class="btn">OK</button></div>
```

```
// 위 HTML을 400×200 창에서 렌더링했을 때 Chrome이 실제로 기록한 paint record (paint 속성 일부 생략)
save                                                                        // 그리기 상태 저장
clipRect      { left: 0, top: 0, right: 400, bottom: 200 }                  // 그릴 영역을 창 크기로 제한
drawRect      { left: 0, top: 0, right: 400, bottom: 200 }      Fill   #FFFFFFFF  // 페이지 배경
drawRect      { left: 20, top: 20, right: 322, bottom: 142 }    Fill   #FFFFFFFF  // .card 배경 (테두리 포함 302×122)
drawRect      { left: 20.5, top: 20.5, right: 321.5, bottom: 141.5 }  Stroke 1px #FFDDDDDD  // .card 테두리
drawRRect     { left: 41, top: 51, right: 121, bottom: 87, radius: 6 }  Fill #FF2563EB    // .btn 배경 (RRect = Rounded Rect)
drawTextBlob  { x: 67.2, y: 74 }                                Fill   #FFFFFFFF  // .btn 글자 "OK"
restore                                                                     // 그리기 상태 복원
```

- 배경 → 테두리 → 내용 순서로 기록한다. 나중에 그린 것이 위에 덮이므로 **기록한 순서대로 겹쳐진다.**
- 실제 명령 목록은 DevTools에서 볼 수 있다 : ⋮ 메뉴 → More tools → Layers 탭 → 왼쪽 목록에서 레이어 선택(ex: `#document`) → 아래 Details 영역의 Paint Profiler 링크 클릭. Chrome이 실행한 그리기 명령과 각 명령이 그린 결과를 확인할 수 있다.

**순서 정하기 : z-index와 stacking context**

- 겹치는 요소는 z-index가 높은 쪽을 나중에 기록해 위에 그려지게 한다.
- **stacking context** : z-index를 비교하는 그룹. 자식의 z-index는 부모가 만든 그룹 안에서만 의미가 있고, 그룹 밖과 비교할 때는 부모의 z-index로 비교된다.
- `position` + `z-index` 외에도 `opacity`가 1 미만이거나 `transform`이 있으면 새 stacking context가 생긴다.

```html
<div style="position: relative; z-index: 1">
  <!-- 9999여도 부모 그룹(z-index 1) 안에서만 유효 -->
  <div style="position: relative; z-index: 9999">자식</div>
</div>
<!-- 부모(1)보다 높아서 위 자식보다 위에 그려짐 -->
<div style="position: relative; z-index: 2">이웃</div>
```

**바로 그리지 않고 명령 목록 단계를 거치는 이유**

- 페이지 일부만 바뀌면(DOM 변경, hover로 색 변경 등) 브라우저는 명령 목록에서 그 부분만 다시 기록할 수 있음 ⇒ 전체를 다시 그리지 않음
- 명령 목록만 넘기면 되므로, 브라우저는 픽셀을 칠하는 무거운 일(래스터)을 메인 스레드가 아닌 다른 곳에 나눠 맡길 수 있다.
    - 화면을 타일로 쪼개 나눠 칠하고, GPU는 많은 픽셀을 동시에 처리하므로 메인 스레드 혼자 순서대로 칠하는 것보다 빠르다.
    - 그동안 메인 스레드는 JS 실행·클릭 처리 같은 다른 일을 할 수 있어 페이지가 덜 버벅인다.

### 레이어와 컴포지팅

- 브라우저는 페이지를 그릴 때 한 장에 전부 그리지 않고, 독립적으로 처리할 수 있는 여러 **레이어**로 나눠서 그린다.
    - DevTools Layers 탭의 3D 그림에서 실제 레이어 구성을 볼 수 있다.
- 브라우저는 `<video>`, `<canvas>`처럼 내용이 계속 바뀌는 요소나 `transform`·`opacity` 애니메이션 같은 특정 CSS가 적용된 요소를 자동으로 별도 레이어로 떼어낸다. 개발자가 `will-change: transform`처럼 "곧 움직일 요소"라는 힌트를 줘서 레이어로 떼게 할 수도 있다.
- 요소가 별도 레이어에 있으면, 브라우저는 그 요소가 움직이거나 투명도가 바뀔 때 다시 그리지 않고 **레이어의 위치·투명도만 바꿔 다시 겹치면** 된다.
    - ex) 사이드 메뉴가 슬라이드로 들어올 때, 메뉴가 별도 레이어면 브라우저는 판 위치만 옮긴다. 한 장에 그려져 있었다면 매 프레임 메뉴와 그 뒤 배경까지 다시 그려야 한다.
    - 단, 레이어마다 메모리를 차지해서 레이어가 너무 많으면 오히려 느려진다 ⇒ 브라우저는 레이어 수를 신중하게 정하고, 개발자도 `will-change`를 남발하지 않는 게 좋다.
- 레이어 구성이 정해지면 메인 스레드는 레이어 정보를 **컴포지터 스레드**에 넘기고, 레이어를 겹치는 일은 컴포지터 스레드가 맡는다.
    - 컴포지팅(합성) : 브라우저가 레이어들을 위치에 맞게 겹쳐 최종 화면 한 장을 만드는 것
    - 컴포지터 스레드는 같은 렌더러 프로세스 안에 있지만 메인 스레드와는 별개의 스레드다.
    - 그래서 JS가 무거운 작업으로 메인 스레드를 붙잡고 있어도, 컴포지터 스레드는 레이어를 옮기고 겹치는 일을 계속할 수 있다 ⇒ **페이지가 멈춘 것 같은데 스크롤은 되는** 이유

### 래스터와 GPU

- 브라우저는 페인트 단계에서 만든 명령 목록을 실제 픽셀로 바꾸고(**래스터**), 레이어들을 겹쳐(**합성**) 최종 화면을 만든다.
    - 래스터(raster) : `drawRect` 같은 그리기 명령을 픽셀 색값으로 바꾸는 것
- 컴포지터 스레드는 레이어를 **타일**이라는 작은 사각형 조각(256×256, 512×512 등)으로 쪼갠다.
    - 타일로 쪼개 두면 브라우저는 지금 화면에 보이는 타일부터 먼저 칠하고, 화면 밖 타일은 나중에 칠할 수 있다.
- 타일마다 명령 목록을 실행해 GPU로 픽셀을 칠하는 작업은 Viz 프로세스(GPU 프로세스)가 담당하고, 결과를 GPU 메모리에 텍스처로 둔다.
    - 텍스처 : GPU 메모리에 올라간 비트맵(픽셀 색값이 나열된 데이터)
    - 렌더러의 컴포지터 쪽 스레드는 "이 타일들을 칠해달라"고 작업을 정리해 Viz에 넘기고, GPU를 쓸 수 없는 환경에서는 이 스레드들이 CPU로 대신 칠한다(fallback raster).
- 컴포지터 스레드는 "어떤 타일을 화면 어디에, 어떤 효과(투명도·transform 등)로 붙일지"를 모아 **컴포지터 프레임**을 만들고, IPC로 Viz 프로세스에 보낸다.
    - IPC : 프로세스끼리 데이터를 주고받는 통신
    - Viz 프로세스 : 크롬에서 화면 그리기의 마지막 단계를 혼자 담당하는 GPU 프로세스.
    - 주소창·탭 바 같은 브라우저 UI(브라우저 프로세스)와, cross-site iframe을 맡은 다른 렌더러 프로세스도 각자 컴포지터 프레임을 만들어 Viz에 보낸다.
- Viz 프로세스는 받은 컴포지터 프레임들을 하나로 합치고(aggregate), GPU로 텍스처를 제자리에 그려 최종 화면을 만든다. 이때 OS별 그래픽 API(Windows는 DirectX, Mac은 Metal, 그 외 OpenGL·Vulkan 등)를 쓴다.
- Chrome 렌더링 파이프라인 요약 : DOM → style → layout → paint → layerize → raster → composite
    - layerize = 레이어로 나누기, raster = 위 1~2단계, composite = 위 3~4단계
- 브라우저가 GPU 작업을 별도 프로세스로 떼어두는 이유
    - **안정성** : GPU 드라이버는 버그가 잦다. 드라이버가 크래시해도 GPU 프로세스만 재시작되고, 탭이나 브라우저 전체는 살아남는다.
    - **보안** : WebGL·canvas는 웹페이지가 GPU에 그리기 명령을 내리는 기능이라, 악성 페이지가 이를 통해 드라이버 취약점을 노릴 수 있다. 그래서 브라우저는 GPU 작업을 권한이 제한된 별도 프로세스에 가둬둔다.

### 그래서 transform/opacity 애니메이션이 빠르다

- 스크롤은 대부분 큰 페이지 텍스처에서 보이는 영역만 옮기는 일 ⇒ 컴포지터가 레이어 위치만 바꾸고 새로 들어오는 부분만 그리면 된다.
- `transform`, `opacity` 애니메이션은 레이아웃을 건드리지 않으므로 **컴포지터 스레드만으로 매 프레임을 만들 수 있다** ⇒ 메인 스레드가 바빠도 60fps 유지 가능.
- `height`, `background-color` 애니메이션은 매 프레임 레이아웃이나 페인트를 다시 해야 하므로, 메인 스레드가 못 따라가면 버벅임(jank)이 생긴다.
- 60fps = 프레임당 약 16.7ms. 메인 스레드가 바쁘면 프레임이 누락되고, DevTools Performance 탭에서 dropped frame으로 확인할 수 있다. `requestAnimationFrame`은 JS 업데이트를 프레임 경계에 맞춰준다.



**컴포지터 스레드도 메인 스레드를 기다리는 경우**

스크롤은 원칙적으로 컴포지터 스레드가 처리한다. 하지만 `wheel`/`touchstart`/`touchmove`에 `preventDefault()`로 스크롤을 취소할 수 있는 리스너가 등록돼 있으면, 컴포지터 스레드는 메인 스레드가 그 리스너를 다 실행할 때까지 기다려야 한다(리스너가 스크롤을 막을지도 모르니까). 메인 스레드가 다른 JS로 바쁘면 그동안 스크롤이 멈칫한다.

- 해결 : 스크롤을 막을 필요가 없는 리스너에는 `addEventListener('touchmove', handler, { passive: true })`처럼 passive 옵션을 준다. passive 리스너는 이벤트를 취소할 수 없으므로, 브라우저는 리스너를 기다리지 않고 바로 스크롤한다. (passive 리스너에서 `preventDefault()`를 호출하면 무시되고 콘솔에 경고가 뜨기도 한다)
- 기본값 : 명세상 `window`, `document`, `document.documentElement`, `document.body`에 단 `wheel`/`touchstart`/`touchmove` 리스너는 passive가 기본 `true`다. 그래서 이 문제는 주로 특정 요소에 리스너를 달았을 때 생긴다. 반대로 이 대상에서 스크롤을 정말 막아야 한다면 `{ passive: false }`를 명시해야 한다.
