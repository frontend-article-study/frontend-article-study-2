# 검증하지 말고 파싱하세요 - 그렇게 하라고 이끌어 주지 않는 언어에서

> 원문: Parse, don't validate — TypeScript edition (Alexis King의 "Parse, Don't Validate"를 TypeScript 맥락으로 풀어낸 글)
> 

## 한 줄 요약

**검사한 결과를 타입에 남겨라.** 검증(validate)은 "괜찮으니 진행해"라고 말하고 결과를 버리지만, 파싱(parse)은 검사한 사실을 **더 정확한 타입으로 인코딩해서 보존**한다. 문자열을 한 번 `Email` 타입으로 파싱하고 나면, 프로그램의 나머지 부분에서는 그 값을 다시 의심할 필요가 없다.

## 검증기의 문제

흔한 검증기 코드는 이런 형태를 띤다.

```tsx
interface User {
  id: number;
  email: string;
  age: number;
}

function isValidUser(user: User): boolean {
  if (!user.email.includes("@")) return false;
  if (user.age < 0 || user.age > 150) return false;
  return true;
}

function sendWelcome(user: User) {
  if (!isValidUser(user)) throw new Error("invalid user");
  // ...나중에, 호출 스택 깊은 곳에서
  emailService.send(user.email, `Welcome, age ${user.age}`);
}
```

문제는 검증이 끝난 뒤에도 `user.email`은 여전히 그냥 `string`이다. 검증은 일어났지만 타입 시스템은 `isValidUser`가 반환되는 순간 그 사실을 잊어버린다. 그래서 검증이 여러 곳에 흩어지고, 어느 것도 기억되지 않는 상태가 된다(=shotgun parsing)

우리가 실제로 원하는 시그니처는 다음과 같다.

```tsx
function sendWelcome(user: ValidUser) {
  emailService.send(user.email, `Welcome, age ${user.age}`);
}
```

- 파서를 거치지 않은 값으로는 `sendWelcome`을 호출할 수 없어야 하고
- 재검사나 방어적 프로그래밍이 필요 없어야 하고
- **타입 자체가 "검증됐다"는 증거** 역할을 해야 한다

Elm 같은 명목적 타이핑 언어는 이러한 타입 처리를 언어 차원에서 지원하여 간단하게 해결 가능하다. 그러나 TypeScript 같은 구조적 타입 언어는 우회가 필요하다.

- **명목 vs 구조적 타이핑**: 타입 호환을 판단하는 기준은 크게 둘이다.
    - **명목 타이핑(nominal)** : 선언된 이름으로 구별해서 구조가 같아도 이름이 다르면 다른 타입(Java·Haskell·Elm·Rust 등)
    - **구조적 타이핑(structural)** : 모양만 맞으면 호환(TypeScript, Go 인터페이스). 그래서 TS에서는 `type Won = { amount: number }`과 `type Dollar = { amount: number }`를 서로 바꿔 넣어도 에러가 안 난다.
- **Elm**: 웹 프론트엔드용 순수 함수형 언어(Haskell 계열). Elm의 타입은 이름으로 구별되는 명목 타입이라, 모듈이 생성자를 숨기면(불투명 타입) 그 타입의 값은 모듈이 제공하는 생성 함수(스마트 생성자)로만 만들 수 있다. 반면 TS는 모양만 같으면 같은 타입으로 보는 구조적 타이핑이라 이게 안 된다.

## 타입스크립트에서 파서 만들기

커뮤니티에서 정착된 방식은 브랜디드 타입으로 우회하는 방법이다.

- **브랜디드 타입(branded type)**: 원시 타입에 존재하지 않는 가짜 속성을 인터섹션으로 붙여 타입을 구별하는 기법. ex) `type Email = string & { readonly __brand: "Email" }`
- 브랜드 필드는 런타임에는 없고 컴파일 시점에만 동작하는 타입 레벨 표시자이며, 일반 `string`은 `__brand`가 없어 `Email`에 할당 불가하다 → `Email`은 파서 함수를 통과해야만 얻을 수 있다.
- 가장 간단한 방식은 위와 같이 문자열 리터럴 속성을 붙이는 방법이지만, 문자열 브랜드는 누구나 같은 리터럴로 위조할 수 있다는 점에서 unique symbol을 활용하기도 한다.
    - unique symbol : Symbol은 호출할 때마다 세상에 하나뿐인 값을 만드는 JS 원시 타입이지만, TS 타입 시스템에서는 같은 symbol로 묶이고 서로 구분하지 못한다. `unique symbol`은 그 고유함을 타입 레벨로 끌어올린 것으로, 정의할 때마다 고유한 타입으로 생성된다. 이 타입은 해당 `const` 선언 하나에만 묶이기 때문에, 심볼을 export하지 않으면 모듈 밖에서는 같은 타입을 재현(위조)할 방법이 없다.
    - ex) `declare const EmailBrand: unique symbol` + `string & { readonly [EmailBrand]: true }`
- 브랜드는 한 방향 : **`Email`**은 여전히 **`string`**에 할당할 수 있음. 도메인 안으로 들어올 때는 명목적으로, 밖으로 나갈 때는 구조적으로 동작한다.

### 만드는 법

다음과 같이 도메인 타입을 unique symbol 브랜드로 정의하고,

```tsx
declare const EmailBrand: unique symbol;
declare const AgeBrand: unique symbol;

type Email = string & { readonly [EmailBrand]: true };
type Age = number & { readonly [AgeBrand]: true };
```

이 타입을 반환하는 파서를 만든다.

```tsx
type ParseError = { kind: "ParseError"; message: string };
type Parsed<T> = { kind: "ok"; value: T } | { kind: "err"; error: ParseError };

function parseEmail(raw: string): Parsed<Email> {
  if (!raw.includes("@")) {
    return { kind: "err", error: { kind: "ParseError", message: "missing @" } };
  }
  // 검사를 마쳤으니, 의도적으로 타입 시스템에 거짓말
  return { kind: "ok", value: raw as Email };
}

function parseAge(raw: unknown): Parsed<Age> {
  if (
    typeof raw !== "number" ||
    !Number.isInteger(raw) ||
    raw < 0 ||
    raw > 150
  ) {
    return { kind: "err", error: { kind: "ParseError", message: "bad age" } };
  }
  return { kind: "ok", value: raw as Age };
}
```

주의할 점 :

- `as Email` 캐스트는 **파서 단 한 곳에서만 허용 ⇒** 파서가 신뢰 경계(trusted boundary)이고, 코드베이스의 나머지에서는 `string`으로부터 `Email`을 만들어낼 수 없다. 파서를 별도 모듈에 두고 그 밖의 `as Brand<...>`는 버그로 취급하면 된다. (ESLint 커스텀 룰로 강제 가능)
- 에러는 불리언 대신 `kind: "ok" | "err"` **판별 유니언**으로 표현한다. 불리언은 세 번째 케이스가 생기는 순간 완전성 검사(exhaustiveness check)가 제대로 작동하지 않는다.
    - true/false로 성공 상태를 표현할 경우, 제 3의 상태(ex: loading)가 생길 경우 처리가 애매해지고 미리 만들어놓은 완전성 검사(모든 경우를 다 처리했는지 컴파일러가 확인해주는 로직)가 깨질 수 있음. 완전성 검사 로직에 대해서는 뒤에서 마저 설명

이를 활용해서 네트워크에서 막 넘어온 원시 타입과 신뢰할 타입을 따로 정의할 수 있으며, 이를 분리해서 추출하는 전체 로직은 다음과 같다.

```tsx
declare const UserIdBrand: unique symbol;
type UserId = number & { readonly [UserIdBrand]: true };

type UnvalidatedUser = {
  id: unknown;
  email: unknown;
  age: unknown;
};

type ValidUser = {
  readonly id: UserId;
  readonly email: Email;
  readonly age: Age;
};

function parseUserId(raw: unknown): Parsed<UserId> {
  if (typeof raw !== "number" || !Number.isInteger(raw) || raw < 0) {
    return { kind: "err", error: { kind: "ParseError", message: "bad id" } };
  }
  return { kind: "ok", value: raw as UserId };
}

function parseUser(raw: unknown): Parsed<ValidUser> {
  if (typeof raw !== "object" || raw === null) {
    return {
      kind: "err",
      error: { kind: "ParseError", message: "not an object" },
    };
  }
  if (!("id" in raw) || !("email" in raw) || !("age" in raw)) {
    return {
      kind: "err",
      error: { kind: "ParseError", message: "missing fields" },
    };
  }
  if (typeof raw.email !== "string") {
    return {
      kind: "err",
      error: { kind: "ParseError", message: "email not a string" },
    };
  }

  const id = parseUserId(raw.id);
  if (id.kind === "err") return id;

  const email = parseEmail(raw.email);
  if (email.kind === "err") return email;

  const age = parseAge(raw.age);
  if (age.kind === "err") return age;

  return {
    kind: "ok",
    value: { id: id.value, email: email.value, age: age.value },
  };
}
```

- 이렇게 할 경우 `parseUser`를 통하지 않고 `ValidUser`를 만드는 경로는 없으며, 검증 결과가 확실해진다.

## TypeScript의 한계

- **as 캐스트가 필요하다** — 위에서 말한 대로 파서 모듈 안에서만 단언하도록 해야 한다.
- **완전성 검사** — Rust의 `match`같은 완전성 검사 전용 문법이 없어서, `switch` + `default`에서 `never` 할당으로 완전성 검사를 흉내낼 수 있다.
    
    ```tsx
    function describe(result: Parsed<ValidUser>): string {
      switch (result.kind) {
        case "ok":
          return `user ${result.value.id}`;
        case "err":
          return `failed: ${result.error.message}`;
        default: {
          const _exhaustive: never = result;
          return _exhaustive;
        }
      }
    }
    ```
    
    이렇게 할 경우 Parsed에 세 번째 변형을 추가하면 never 할당이 실패하고, 컴파일러가 어디를 고쳐야 하는지 알려준다.
    
- **`satisfies`** — 타입에 맞는지 검사하되 넓히지(widen) 않는, "캐스트의 예의 바른 버전". 리터럴 타입을 유지하면서 안전성을 얻는다.
- **`JSON.parse`는 `any`를 반환한다** — 받자마자 `const raw: unknown = JSON.parse(input)`으로 붙이고 파서에 넘기는 것이 좋다.

## Zod는 어떤가요?

Zod / io-ts / valibot 등과 같은 검증 라이브러리를 활용하면 하나의 스키마 정의에서 파서와 타입을 동시에 얻을 수 있으므로, 위 수작업 코드를 편하게 작성할 수 있다.

```tsx
import { z } from "zod";

const ValidUserSchema = z.object({
  id: z.number().int(),
  email: z.string().email().brand<"Email">(),
  age: z.number().int().min(0).max(150).brand<"Age">(),
});

type ValidUser = z.infer<typeof ValidUserSchema>;

const result = ValidUserSchema.safeParse(rawInput);
```

이 코드는 위 수작업 코드와 같은 역할을 한다. `.brand()`도 똑같이 순수 타입 레벨에만 존재하고, 런타임에는 아무 일도 일어나지 않는다.

다만 Zod를 쓸 때도 마찬가지로 타입 단언을 남용하지 않고 모든 경계에서 파싱하기로 일원화하는 규율이 필요하다.

## 더 작은 원칙

> 기억이 아니라 타입 시스템이 증거를 짊어지게 하라.
> 

무언가를 검사하고 그 결과를 타입에 인코딩하지 않으면, 미래의 나에게 "기억해"라고 요구하는 셈이다. 미래의 나는 기억하지 못한다. 검증기는 뚫리지만 파서는 뚫리지 않는다.

TypeScript에서의 실천 3가지:

1. 명목 타입에 가까운 정체성을 위한 **브랜디드 타입**
2. 정직한 에러 처리를 위한 **판별 유니언**
3. `unknown`(외부에서 온 것)과 도메인 타입(신뢰를 얻은 것) 사이의 **엄격한 경계**

서로 다른 세 파일에서 같은 걸 검사하는 세 번째 방어적 `if`를 추가하고 있다면, 파싱했어야 할 곳에서 검증하고 있는 것이다.
