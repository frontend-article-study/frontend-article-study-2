캡처 위치와 호출 위치

클로저를 “함수가 바깥 변수를 기억한다”로만 알면 놓치는 것이 있다. react-router 상대경로 이동을 추적하다 한 번 틀린 결론을 냈던 사례를 최소 예제로 줄여서 정리했다.

한 줄 요약

함수가 어떤 값을 보는지는 그 함수가 정의된 자리가 정한다. 어디로 넘겨져서 어디서 실행되든 바뀌지 않는다.

§1클로저 = 함수 + 그 함수가 태어난 환경

makeCounter.js클로저의 최소 형태
function makeCounter() {
  let n = 0            // makeCounter의 지역 변수
  return () => ++n     // 이 함수가 n을 붙들고 밖으로 나간다
}

const c = makeCounter()
c() // 1
c() // 2
  • 현상 — makeCounter는 이미 끝났는데 n은 살아 있다.
  • 이유 — 반환된 함수가 자기가 정의된 렉시컬 환경에 대한 참조를 들고 나갔다.
  • 핵심 — 값을 복사해 가는 게 아니라 환경을 붙들고 간다. 그래서 n이 바뀌면 클로저가 보는 값도 같이 바뀐다.
loop.js“환경을 붙든다”가 드러나는 고전 예제
// var: 함수 스코프 — 세 콜백이 "같은" 환경 하나를 공유한다
for (var i = 0; i < 3; i++) setTimeout(() => console.log(i))
// 3 3 3

// let: 반복마다 새 바인딩 — 콜백마다 "다른" 환경을 붙든다
for (let i = 0; i < 3; i++) setTimeout(() => console.log(i))
// 0 1 2

두 코드의 차이는 콜백이 아니라 콜백이 태어난 환경의 개수다. 클로저 문제를 풀 때 함수 본문만 들여다보면 답이 안 나오는 이유.

§2렉시컬 스코프 — “정의 위치”가 정한다

lexical.js호출 위치는 스코프에 관여하지 않는다
const x = 'outer'
function f() { return x }        // f의 스코프는 여기서 결정된다

function g() {
  const x = 'inner'
  return f()                     // 호출은 여기서 하지만
}

g() // 'outer'  ← 'inner'가 아니다
  • 규칙 — 함수가 보는 변수는 소스 코드에서 그 함수가 쓰인 자리로 결정된다.
  • 불변 — 나중에 어디서 호출되든 바뀌지 않는다. 그래서 “정적(static) 스코프”라고도 한다.
  • 대비 — this는 반대로 호출 위치가 정한다(동적).

한 언어 안에 정의 위치 규칙(변수)과 호출 위치 규칙(this)이 공존하는 것이 혼란의 큰 원인이다. 헷갈릴 때 이 둘을 먼저 분리하자.

§3리액트 훅은 클로저 팩토리다

  • 여기서부터가 본론. 실무에서 흔한 구조를 최소한으로 줄인 예제다.
  • 결제 플로우가 splat 라우트 아래에 있고, 그 안에서 다시 <Routes>로 단계를 나눈다.
routes.jsx라우트 정의 — receipt는 payment의 형제다
<Route path="/checkout" element={<CheckoutLayout />}>
  <Route path="payment/*" element={<PaymentFlow />} />   // splat 라우트
  <Route path="receipt"  element={<ReceiptPage />} />
</Route>
PaymentFlow.jsxnavigate가 만들어지는 곳과 실행되는 곳
function PaymentFlow() {
  const navigate = useNavigate()          // ① 여기서 만들어진다 (컴포넌트 본문)

  return (
    <Routes>
      <Route
        path="done"
        element={
          <PaymentDonePage
            onNext={() => navigate('../receipt')}
          />
        }
      />
    </Routes>
  )
}

function PaymentDonePage({ onNext }) {
  return <button onClick={onNext}>영수증 보기</button>   // ② 여기서 실행된다
}
  • 질문 — 현재 URL이 /checkout/payment/done일 때, '../receipt'의 ..는 어디를 기준으로 한 걸음인가?
  • 답은 useNavigate의 구현에 있다.
react-router 7.18.0 · dist/development/chunk-4ZMWKKQ3.mjsL5915–5963 · 요약 발췌
function useNavigateUnstable() {
  let { matches } = React2.useContext(RouteContext);        // ① 지금 이 위치의 matches를 읽고
  let routePathnamesJson = JSON.stringify(getResolveToMatches(matches));

  let navigate = React2.useCallback((to, options = {}) => {
    let path = resolveTo(
      to,
      JSON.parse(routePathnamesJson),                    // ② 클로저로 캡처해서 쓴다
      locationPathname,
      options.relative === "path"
    );
    (!!options.replace ? navigator.replace : navigator.push)(path, ...);
  }, [basename, navigator, routePathnamesJson, locationPathname]);

  return navigate;   // ③ 이 함수는 트리 어디로 내려가든 ①의 값을 들고 다닌다
}
  • 훅이 하는 일 — 함수를 하나 만들어 돌려준다.
  • 그 함수의 정체 — RouteContext에서 읽은 matches를 캡처한 클로저.
  • 결과 — 훅을 호출한 그 자리의 라우트 정보가 함수 안에 굳어 들어간다.

§4함수는 내려가고, 환경은 남는다

  • ① 캡처 — useNavigate()가 실행된 자리는 PaymentFlow의 컴포넌트 본문. 라우트로 보면 payment/* element 자리다.
  • ② 호출 — 만들어진 navigate는 onNext prop에 담겨 done 페이지의 버튼으로 내려간다.

§5캡처된 스택이 다르면 결과가 다르다

  • matches는 getResolveToMatches를 거쳐 경로 스택으로 바뀐다.
  • 여기에 함정이 하나 더 있다.
react-router 7.18.0 · chunk-4ZMWKKQ3.mjsL919–924
function getResolveToMatches(matches) {
  let pathMatches = getPathContributingMatches(matches);
  return pathMatches.map(
    (match, idx) => idx === pathMatches.length - 1
      ? match.pathname        // 마지막 칸만 pathname (splat 포함 전체 경로)
      : match.pathnameBase
  );
}
  • 규칙 — 마지막 항목만 pathnameBase가 아니라 pathname을 쓴다.
  • 영향 — payment/*는 splat 라우트라 pathname에 done까지 포함된다.
  • 결론 — 스택의 마지막 칸 하나에 두 세그먼트가 들어 있고, .. 한 번이 둘 다 지운다.
A · PaymentFlow 본문에서 캡처 → /checkout/receipt B · done element에서 캡처 → /checkout/payment/receipt

참고 — relative: 'path'는 다른 기준을 쓴다

  • 동작 — 이 스택 계산을 아예 건너뛰고, 현재 URL에서 세그먼트를 하나 떼어낸다(resolvePathname).
  • 장점 — 캡처 위치에 영향을 받지 않는다.
  • 대가 — 의미가 달라진다. 라우트 계층이 아니라 URL 문자열 기준이다.
navigate('../receipt') → 캡처 위치에 따라 갈림 (위 결과) navigate('../receipt', { relative: 'path' }) → 항상 /checkout/payment/receipt

두 모드가 우연히 같은 답을 낼 때도 많아서 더 헷갈린다. “상대경로가 왜 이렇게 풀리지?”를 볼 때는 어느 모드인지와 어디서 캡처했는지를 같이 확인해야 한다.

§6오판의 해부

이 구조를 처음 분석했을 때 틀린 결론을 냈다가 뒤집혔다.

틀린 추론

  • “버튼이 done 안에 있으니 ..의 기준점도 done이다.”
  • → /checkout/payment/receipt인데 매칭 라우트가 없으니 빈 화면이 뜰 것이다.
  • 무엇이 문제였나 — 호출 위치로 스코프를 추론했다. §2의 렉시컬 스코프 위반.
  • 실제 — /checkout/receipt로 정상 이동하고 있었고 화면도 정상이었다.

왜 이 오판이 유독 그럴듯했나

  • 검증한답시고 done element 안에서 useResolvedPath('../receipt')를 찍으면 진짜로 B의 값이 나온다.
  • 그 훅은 거기서 새로 캡처하기 때문이다.
  • 함정 — 실제로 실행되는 navigate는 그 클로저가 아니다. 확인하려고 찍어본 값이 오히려 오판을 굳혀줬다.

무엇이 결론을 뒤집었나

  • 코드를 더 읽는 대신 createMemoryRouter로 같은 중첩 구조를 재현해 실행했다.
  • 클릭 한 번으로 끝났다.
[클릭 후] pathname = /checkout/receipt [클릭 후] 렌더 = ReceiptPage

교훈 — 클로저와 컨텍스트가 얽히면 코드를 읽어서 얻은 확신은 신뢰도가 낮다. 캡처 위치를 특정할 수 없으면 재현해서 실행하는 편이 빠르다.

§7stale closure와는 다른 문제다

리액트에서 “클로저 버그”라고 하면 보통 stale closure를 떠올린다. 이 건은 그게 아니다.

stale closure란

  • 정의 — 함수가 예전 렌더의 값을 붙든 채 남아 있어, 화면은 갱신됐는데 그 함수만 옛날 값을 보는 상태.
  • 발생 조건 — 함수를 한 번 만들어 어딘가에 등록해 두고(타이머·이벤트 리스너·구독), 값이 바뀌어도 다시 만들지 않을 때.
staleClosure.jsx가장 흔한 형태
function Counter() {
  const [count, setCount] = useState(0)

  useEffect(() => {
    const id = setInterval(() => {
      console.log(count)   // 언제나 0 — 첫 렌더의 count를 붙들고 있다
    }, 1000)
    return () => clearInterval(id)
  }, [])                   // ← deps가 비어 있어 effect가 다시 돌지 않는다

  return <button onClick={() => setCount(count + 1)}>{count}</button>
}
  • 버튼을 눌러 count가 3이 돼도 콘솔에는 계속 0이 찍힌다.
  • 원인 — setInterval에 넘긴 콜백은 첫 렌더에 만들어졌고, 그때의 count(=0) 환경을 붙들고 있다. deps가 비어 있으니 effect가 다시 돌지 않아 새 콜백으로 교체되지도 않는다.
  • 축 — 문제는 “어디서 만들어졌나”가 아니라 “언제 만들어졌나”다.

이번 사례는 왜 다른가

  • navigate는 useCallback 의존성 배열에 routePathnamesJson이 들어 있어 값이 바뀌면 새로 만들어진다. 값은 항상 최신이다.
  • 시간 축은 멀쩡하고, 위치 축만 문제였다.
stale closure이번 사례
축 언제 캡처했나 · 시간 어디서 캡처했나 · 위치
증상 값이 한 렌더 뒤처져 있다 값은 최신인데 기준점이 다르다
전형적 원인 deps 누락, 리스너 등록 후 미갱신 훅 호출 위치와 함수 실행 위치의 분리
해결 방향 deps 수정, ref로 최신값 참조 훅을 원하는 위치로 이동
또는 기준점 명시(relative: 'path', 절대경로)

진단 순서 — “값이 이상하다”면 시간 축, “값은 맞는데 결과가 이상하다”면 위치 축.
