# 이해가 새로운 병목이다 (Understanding is the new bottleneck)

> Geoffrey Litt (Notion, Design Engineer) / 2026.07 AI Engineer 컨퍼런스 발표
> 

## 한 줄 요약

- 코드 생산은 더 이상 병목이 아니다. 이제 병목은 `인간의 이해`다
- 그리고 그 이해 자체를 AI로 가속할 수 있다

## 문제 정의

- 에이전트가 점점 더 많은 코드를 써주고, 우리는 따라잡기 어려워지고 있음
- 하지만 코드를 이해하는 방법이 `diff를 한 줄씩 읽기` 하나뿐인 것은 아님
    - 이 발표는 "더 나은 이해 방법"에 대한 이야기

## 왜 이해해야 하는가

### 흔한 답: 검증하려고 (verify)

- 에이전트의 작업이 맞는지 확인 — 스펙에 부합하는가, 아키텍처가 괜찮은가
- 그런데 이건 결국 `👍 / 👎` 판단에 가까움
- 문제는, 에이전트가 자기 작업을 스스로 검증하는 능력이 계속 좋아지고 있다는 것
    - 검증이 이유의 전부라면, 인간의 자리는 점점 사라짐

### 진짜 답: 참여하려고 (participate) ⭐

- 프로젝트는 단 한 번의 루프가 아니라, 에이전트와 주고받는 `수많은 루프`
- 시스템에 대한 이해 = 다음 아이디어를 떠올리는 능력의 재료
    - 머릿속에 개념이 풍부해야 "이걸 어떻게 발전시킬까"를 유창하게 사고할 수 있음
    - 그 유창함이 없으면 프로젝트에 대한 참여 자체가 제한됨

### 인지 부채 (Cognitive Debt)

- Margaret Storey, Simon Willison이 이야기한 개념
- 기술 부채와 같은 구조: 단기적으로는 몰라도 넘어갈 수 있지만, 결국 대가를 치름
- 최악의 상태: "관여한 인간들이 그냥 흐름을 놓쳐버린" 상태

## 어떻게 이해할 것인가 — 교육에서 훔쳐오기

- 이해를 전달하는 문제는 인류가 처음 푸는 문제가 아님 → `교육`에서 아이디어를 가져오자

### 기법 1. 설명 (Explanations)

- 에이전트가 작업을 끝낸 순간은 곧 `설명(artifact)`을 만들 기회
- 가장 순진한 형태 = 날것의 code diff
- 질문: **"최고의 설명이란 어떤 모습일까?"**
    - 나에게 잘 설명해주려고 디테일까지 신경 쓰는 팀이 있다면, 그 경험은 어떤 느낌일까
- 저자의 답: `/explain-diff` 스킬 (HTML / Markdown / Notion 문서로 출력)
    - 원칙 1. **배경부터 가르쳐라**
        - 무엇이 바뀌었는지 말하기 전에, 원래 무엇이 있었는지부터(원래 시스템이 어떻게 돌아가고 있었는지)
    - 원칙 2. **디테일보다 직관 먼저**
        - 코드 이전에 목표를 한 문장으로 (e.g. "2D 드로잉 트릭으로 정원을 입체적으로 느껴지게")
            - 코드 대신 본질을 느끼게 하기
        - 관련 개념 설명 (예: isometric projection이 무엇인가)
    - 원칙 3. **인터랙티브 도표**
        - 오브젝트를 드래그하며 좌표 변화를 직접 보고 직관 얻기
    - 원칙 4. **Literate diff (산문형 코드 디프)**
        - 일반 diff: 알파벳 순으로 나열된 파일 더미, 설명 없음
        - literate diff: 납득 가능한 순서로 산문처럼 서술 + 코드 조각 임베드
        - → 코드의 흐름을 따라가게 되니 날것의 diff보다 리뷰가 빠름
    - 결과물: "설명 패킷". diff도 여전히 읽지만, 항상 이걸 먼저 읽음
        - 인쇄해서 카페에서 읽기도 함 (AI가 인터랙티브한 활동을 정적인 종이 리포트로 되돌려놓는 아이러니)
- 남은 문제: **읽는 건 힘든 일이다**
    - Andy Matuschak: "책은 작동하지 않는다(books don't work)"
    - 읽었다고 착각하기 너무 쉬움 (실제로는 이해도 기억도 못함)
- 해결: **퀴즈** (Quantum Country의 spaced repetition 아이디어 차용)
    - 설명 문서 하단에 이번 변경에 대한 5문제 인터랙티브 퀴즈
    - 저자의 규칙: `퀴즈를 통과하기 전에는 코드를 남에게 넘기지 않는다`
        - 남의 코드를 리뷰할 때도 동일하게 적용
    - **퀴즈 = 속도 조절기(speed regulator)** ⭐
        - AI와 일하면 루프가 인간의 이해 속도보다 빨리 돌기 쉬움
        - 퀴즈는 그에 맞서는 힘: "내가 진짜 이해했나?"를 기계적으로 묻게 만듦

### 기법 2. 마이크로월드 (Micro-worlds)

- Seymour Papert의 `Mathland에 살기`에서 출발
    - 프랑스어를 배우려면 프랑스에 살듯, 수학을 배우려면 수학의 나라에 산다
    - 호기심의 자연스러운 결과로 배우게 되는 환경을 만들 수 있을까?
- 코드에 적용하면: **직접 들어가 살면서 시스템의 작동 방식을 자연히 체득하는 세계를 만들 수 있을까?**
- 사례 1. Prolog 인터프리터 디버거
    - 내부에서 무슨 일이 일어나는지 감이 안 잡혀서, 에이전트와 함께 디버거를 제작
    - 실행을 시간 순으로 스크럽하고, 스택과 각 단계에서 적용된 규칙을 확인
    - 핵심 차이: `에이전트가 디버깅하게 두는 것` vs `내가 디버깅할 도구를 만드는 것`
        - 후자만이 이해를 남김
- 사례 2. 웹사이트 프레임워크 마이그레이션 "커맨드 센터"
    - Claude가 짜준 포팅 스크립트는 리뷰가 거의 불가능 ("그럴듯해 보이네" 이상 말할 수 없음)
    - 그래서 포팅을 직접 단계별로 실행하는 게임 같은 UI를 요청
        - 버튼을 누르며 한 단계씩 진행, 파일 트리 변화 관찰, 구/신 사이트 나란히 실행
    - 결과: 손으로 직접 한 것과 비슷한 이해를, 훨씬 빠르게
- 요점: **에이전트는 "다른 코드를 이해하게 돕는 코드"를 짜줄 수 있다** ⭐

## 결론: 루프에서 빼는 데도, 더 깊이 넣는 데도 쓸 수 있다

- **"AI는 우리를 루프에서 빼는 데도 쓸 수 있지만, 루프에 더 깊이 넣는 데도 쓸 수 있다. 후자가 컴퓨팅의 원래 목적이었다."** ⭐
- 두 가지 쓰임새
    - `대신하기(자동화)`: 사람이 하던 일을 AI가 대신함 → 사람은 루프 밖으로
    - `키우기(증강)`: AI가 사람의 이해와 사고 능력 자체를 끌어올림 → 사람은 루프 안으로 더 깊이
    - 같은 도구도 어느 쪽을 노리느냐에 따라 달라짐
        - 에이전트가 대신 디버깅해준다 → 대신하기
        - 에이전트가 나를 위해 디버거를 만들어주고 내가 직접 들여다본다 → 키우기
        - 앞의 마이크로월드 사례가 정확히 이 대비
- 그래서 저자는 낙관적
    - 자동화가 틀렸다는 게 아니라, **자동화만 남기고 이해를 놓치는 것**이 문제
    - AI 덕분에 시뮬레이션·설명·이해 도구를 만드는 비용이 폭락 → 오히려 지금이 기회
    - 코드에 한정된 이야기가 아님. "인간이 세상이 어떻게 돌아가는지 이해하는 것" 전반에 대한 이야기
    - 올바른 도구를 만든다면, 우리는 그 어느 때보다 세상을 잘 이해할 수 있다. 그건 우리에게 달렸다
