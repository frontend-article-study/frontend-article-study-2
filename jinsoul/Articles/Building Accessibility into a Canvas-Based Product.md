- 원문: https://www.figma.com/blog/building-accessibility-into-a-canvas-based-product/

## 시작하며

Figma의 캔버스는 전통적인 HTML 웹 앱으로는 얻기 어려운 성능을 제공한다.

Figma의 캔버스는 비디오 게임과 비슷하게, 성능을 높이기 위해 브라우저 대신 직접 렌더링을 담당한다. 이를 통해 무한 확대·축소와 실시간 멀티플레이어 협업 같은 기능을 제공할 수 있다.

- Figma는 일반적인 HTML·DOM 요소로 디자인 레이어를 하나씩 렌더링하는 대신, 자체 렌더링 엔진으로 디자인 데이터를 계산해 Canvas에 그린다. 이 방식은 복잡한 디자인 문서와 확대·축소를 효율적으로 처리하는 데 유리하다.

하지만 Figma는 캔버스를 렌더링할 때 전통적인 HTML과 DOM을 사용하지 않는다. 따라서 브라우저가 기본적으로 제공하는 접근성 기능도 얻지 못한다.

Figma는 더 많은 사람이 사용할 수 있도록 접근성을 개선하기 위해, Figma 디자인과 동기화된 **Mirror DOM 구조**를 만들었다.

이를 통해 다음과 같은 기능을 지원할 수 있게 됐다.

- 스크린 리더로 Figma 파일 탐색
- 변경 사항을 음성으로 안내
- 키보드로 편집기 조작

## 브라우저의 접근성 트리

브라우저 엔진에는 접근성 트리라는 개념이 있다.

접근성 트리는 보조 기술이 작동하는 데 필요한 비시각적 정보를 문서에서 추출해 만든 데이터 구조다.

예를 들어 스크린 리더 사용자가 “다음 입력 필드로 이동” 명령을 실행하면, 접근성 트리가 스크린 리더에게 다음 위치를 알려준다.

브라우저는 다음 정보를 바탕으로 접근성 트리를 만든다.

- DOM
- 의미 있는 HTML 요소
- ARIA 속성
- 추가로 계산된 상태 정보

일반적인 웹 앱에서는 각각의 컴포넌트가 자신만의 DOM 요소를 가진다.

```jsx
<button>저장</button>
<p>저장되었습니다.</p>
<img alt="프로필 이미지">
```

Figma의 **디자인 편집 영역**은 각 디자인 요소를 HTML 요소로 만들어 화면에 표시하지 않고, Canvas에 그래픽으로 그린다.

```jsx
<canvas></canvas>
```

따라서 Figma의 캔버스에는 디자인 레이어가 아무리 많아도 포커스를 유지하는 `<input>` 요소가 하나뿐이다. 그 결과 브라우저가 만든 Figma 파일의 접근성 트리는 사실상 비어 있었다.

```jsx
브라우저 DOM
├─ Figma 앱 UI
├─ Canvas
└─ 포커스 유지용 input 하나
```

```jsx
Canvas 클릭
↓
숨겨진 input에 포커스
↓
키보드 입력을 Figma가 받음
↓
선택된 디자인 레이어를 움직임
```

이를 해결하기 위해 Figma는 캔버스를 위한 DOM 요소를 추가했다. 이 요소들은 화면을 보는 사용자에게는 보이지 않지만, 스크린 리더가 Figma 파일을 탐색하고 편집할 수 있도록 한다.

## 시스템이 작동하는 방식

Figma의 캔버스를 렌더링하는 데이터 구조는 **`scenegraph`**다.

- **scenegraph:** 화면을 구성하는 요소들을 계층 구조로 정리한 내부 데이터

```jsx
페이지
└─ 상품 카드
   ├─ 이미지
   ├─ 상품명
   ├─ 가격
   └─ 구매 버튼
```

Figma는 캔버스 뒤에서 보이지 않도록 `scenegraph`의 접근성에 필요한 부분을 반영하는 DOM 요소를 렌더링한다.

이 과정에는 네 가지 시스템이 함께 작동한다.

1. Figma 내부의 접근성 트리
2. 접근성 트리를 참고해 DOM 요소를 생성하는 Mirror DOM React 컴포넌트
3. Canvas의 선택 상태와 DOM 포커스를 양방향으로 동기화하는 시스템
4. 탐색과 직접 관련되지 않은 변경 사항을 알리는 시스템

## 1. 내부 접근성 트리

Figma의 디자인 요소는 일반적인 HTML 요소가 아니라 Canvas에 그려지기 때문에, 브라우저는 각 요소의 역할과 구조를 자동으로 알 수 없다.

그래서 Figma는 scenegraph와 레이어 정보를 분석해 각 요소의 이름, 역할, 부모·자식 관계, 현재 상태 등을 정리하고, 이를 **Figma 내부 접근성 트리**로 만든다.

이때 접근성 트리에 포함할 정보는 사용자의 상황에 따라 달라진다.

- 프로토타입을 보는 경우: 텍스트, 버튼, 이미지처럼 최종 사용자에게 필요한 정보
- 디자인을 편집하는 경우: 레이어 구조, 부모·자식 관계, 오토 레이아웃, 선택 상태처럼 편집에 필요한 정보

## 2. Mirror DOM

접근성 트리가 준비되면 Figma는 이를 바탕으로 DOM을 생성한다.

이 작업은 각 디자인 레이어의 접근성 트리 변화를 구독하는 React 컴포넌트가 담당한다.

```jsx
function ScreenReaderElement({ layerId }: { layerId: string }) {
  const { label, role, children } =
    useAccessibleSummary(layerId);

  return <div role={role} ariaLabel={label}>
    {children.map((c) =>
      <ScreenReaderElement
        key={c}
        layerId={c}
      />
    )}
  </div>
}
```

Figma는 접근성 트리를 변경할 때 최소한의 변경만 적용한다. 그리고 React가 DOM 변경도 최소화하도록 한다.

## Mirror DOM의 위치

Mirror DOM은 Canvas의 디자인을 화면에 그대로 복제하는 것이 아니다. 대신 Canvas의 각 디자인 요소에 대응하는 접근성용 DOM을 만들고, 필요한 요소를 Canvas와 같은 위치에 배치한다.

- Canvas: 사용자가 실제로 보는 디자인
- Mirror DOM: 스크린 리더와 보조 기술이 읽는 DOM
- 위치 정보: Canvas의 요소와 Mirror DOM 요소가 서로 대응되도록 유지

예를 들어 Canvas의 버튼 디자인 요소가 오른쪽 아래에 있다면, Mirror DOM의 버튼도 같은 위치·크기·회전 정보를 가진다.

```
Canvas의 버튼
      ↕
Mirror DOM의 버튼
```

Figma는 레이어의 위치, 크기, 확대·축소, 회전, 기울기 정보를 CSS에 반영한다. 그래야 화면 확대 도구나 포커스 표시가 현재 요소의 위치를 정확히 찾을 수 있다.

따라서 Mirror DOM은 화면에서 보이지 않더라도 레이아웃과 위치 정보는 유지해야 한다. 이를 완전히 제거하는 `display: none` 방식은 사용할 수 없다.

```jsx
position: fixed;
width: 1121px;
height: 876px;
opacity: 0;
overflow: hidden;
pointer-events: none;
visibility: visible;
```

## 3. 선택 상태와 포커스 동기화

포커스는 사용자가 현재 상호작용하고 있는 요소를 나타내는 키보드 시스템의 상태다.

스크린 리더와 키보드만 사용하는 사용자는 `Tab` 키를 눌렀을 때 시각적 화면의 흐름과 일치하는 방식으로 포커스가 이동하기를 기대한다.

하지만 Figma에서 선택 상태와 포커스는 항상 동일하지 않다.

```jsx
Canvas 하나
focus-target input 하나
```

```jsx
사용자: Tab을 눌러 Button 레이어로 이동
Figma: Button 레이어를 내부적으로 선택
브라우저: 여전히 같은 Canvas에 포커스
스크린 리더: 어떤 Button인지 모름
```

예를 들어 드롭다운에서 항목을 선택한 뒤 `Tab` 키를 눌러 제출 버튼에 포커스를 이동할 수 있다.

Figma 캔버스를 탐색할 때 `Tab` 키는 시스템 키보드 포커스를 바꾸지 않고 선택된 노드만 변경할 수 있다.

이 경우 캔버스 전체가 스크린 리더에게 하나의 큰 탐색 대상으로 보일 수 있다.

이를 해결하기 위해 Figma는 Canvas의 선택 상태와 Mirror DOM의 시스템 포커스를 양방향으로 동기화했다.

```
Canvas에서 노드 선택
→ 해당 DOM 요소에 포커스

스크린 리더가 DOM 요소로 이동
→ Canvas의 해당 노드 선택
```

```jsx
Tab
→ Button 레이어 선택
→ Mirror DOM의 버튼 요소에 포커스
→ 스크린 리더: “구매하기, 버튼”
```

이 시스템을 통해 VoiceOver rotor와 같은 스크린 리더 기능으로도 Figma 캔버스의 노드를 선택할 수 있다.

## 4. 동작과 변경 사항 안내

내부 접근성 트리와 Mirror DOM은 Figma 파일의 내용을 보조 기술에 전달한다.

하지만 편집 기능에서는 이것만으로 충분하지 않다.

화면을 볼 수 있는 사용자에게는 명확한 동작도, 스크린 리더 사용자에게는 추가 안내가 필요할 수 있다.

예를 들어 레이어를 조금씩 이동하는 동작은 시각적으로는 바로 확인할 수 있지만, 스크린 리더 사용자에게는 변화가 보이지 않는다.

Figma는 이를 위해 브라우저와 ARIA 표준이 제공하는 `live region`을 사용한다.

- 화면의 내용이 바뀌었을 때 스크린 리더가 그 내용을 자동으로 읽게 하는 기능

Figma는 화면에 표시되는 토스트에는 `live region` 마크업을 추가하고, 시각적으로는 토스트가 필요하지 않은 동작에는 보이지 않는 `live region` 안내를 별도로 제공한다.

또한 화면을 보는 사용자에게는 중복처럼 느껴질 수 있는 변화도, 스크린 리더 사용자에게는 별도의 보이지 않는 안내로 제공한다.

예를 들어 방향키로 레이어를 한 픽셀씩 다섯 번 이동하면, 다섯 개의 메시지를 반복해서 읽는 대신 하나의 메시지로 합칠 수 있다.

```jsx
<div aria-live="polite">
  레이어를 5픽셀 이동했습니다.
</div>
```

여러 이벤트가 짧은 시간 안에 같은 종류로 발생하면 하나로 합치는 방식이다.

## 현재 구현된 내용과 앞으로의 계획

Figma의 접근성 개선은 여러 해에 걸쳐 진행됐다.

- 2022년: 프로토타입 뷰어에서 시작
- 2023년: FigJam으로 확장
- 2024~2025년: Design, Dev Mode, Slides에 접근성 개선 적용
- 키보드 전용 조작 기능 추가
- 스크린 리더 경험 개선
- 향상된 대비 모드 추가
- 접근성 관련 기능 지속 개선

Figma는 새로운 기능을 설계하고 개발하고 배포할 때 접근성 지원을 함께 검토하고 있다고 설명한다.

또한 Figma의 접근성 관련 맥락을 제품 개발 조직 전체로 확장하기 위해 내부 도구와 AI 에이전트에도 투자하고 있다.

## Figma를 사용하는 디자이너를 위한 기능

Figma는 Figma 자체의 접근성뿐 아니라, Figma를 사용해 접근성 있는 제품을 만드는 사람을 위한 기능도 제공한다.

예를 들어:

- 색상 조합이 접근성 기준을 충족하는지 확인
- 보이는 레이어 이름을 지정해 스크린 리더에 전달
- 디자인 시스템과 디자인을 비교
- 낮은 대비를 감지
- WCAG 2.0 AA·AAA 기준에 맞는 색상 제안
