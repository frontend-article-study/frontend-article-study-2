## 1. 들어가며

요즘 개발자는 AI를 정말 많이 사용한다.

예전에는 검색하고, 문서를 읽고, 직접 코드를 작성하면서 문제를 해결했다면, 이제는 AI에게 자연어로 요청하면 꽤 그럴듯한 코드를 받을 수 있다.

예를 들어 이런 작업들이 가능하다.

- 컴포넌트 생성
- CSS 스타일링
- API 연결
- 리팩토링
- 테스트 코드 작성
- 에러 해결
- 문서 요약

AI는 개발 속도를 빠르게 만들어준다.

하지만 여기서 한 가지 질문이 생긴다.

> AI가 코드를 대신 만들어준다면, 개발자는 기본기를 덜 알아도 괜찮을까?
> 

이 글의 결론은 반대다.

AI가 코드를 더 빠르게 만들수록, 개발자의 기본기는 더 중요해진다.

---

## 2. 원문의 핵심 주장

원문의 제목은 **“Is AI causing a repeat of frontend’s lost decade?”** 이다.

직역하면 다음과 같다.

> AI는 프론트엔드의 잃어버린 10년을 반복하게 하는가?
> 

이 글은 단순히 “AI 시대에도 기본기가 중요하다”는 이야기를 하지 않는다.

더 정확히는, 프론트엔드가 지난 10년 동안 겪었던 **탈숙련화**가 AI 시대에 프로그래밍 전체에서 반복될 수 있다고 말한다.

핵심 주장은 다음과 같다.

> AI 코딩은 프론트엔드가 지난 10년 동안 겪었던 “기본기 상실”을 프로그래밍 전체에서 반복하게 만들 수 있다.
> 

여기서 중요한 키워드는 **탈숙련화**다.

탈숙련화란 어떤 작업을 수행하는 데 필요했던 전문적인 지식과 숙련이 도구나 프로세스에 의해 가려지거나 약화되는 현상을 말한다.

---

## 3. 프론트엔드는 이미 한 번 탈숙련화를 겪었다

프론트엔드는 원래 브라우저라는 환경을 깊게 이해해야 하는 분야였다.

프론트엔드 개발자는 단순히 화면을 예쁘게 만드는 사람이 아니라, 사용자가 실제로 사용할 수 있는 인터페이스를 설계하고 구현하는 사람이었다.

예전 프론트엔드 개발에 중요했던 지식은 다음과 같다.

- 의미 있는 HTML
- CSS 레이아웃
- 브라우저별 차이
- 접근성
- 점진적 향상
- 네트워크 성능
- 이미지 최적화
- 폼과 기본 브라우저 동작
- 인터페이스 설계
- 사용자 테스트

하지만 React, Next.js 같은 프레임워크와 복잡한 툴링이 등장하면서 많은 개발자가 브라우저 자체보다 프레임워크 사용법에 더 집중하게 되었다.

프레임워크는 매우 유용하다.

복잡한 UI를 효율적으로 만들 수 있고, 상태 관리, 라우팅, 서버 렌더링 같은 문제를 체계적으로 다룰 수 있게 해준다.

하지만 동시에 이런 문제도 생긴다.

> 프레임워크는 브라우저의 복잡성을 감추지만, 그 복잡성이 사라지는 것은 아니다.
> 

즉, 프레임워크를 잘 쓰는 것과 프론트엔드를 잘하는 것은 완전히 같은 의미가 아니다.

---

## 4. “프론트엔드의 잃어버린 10년”이란 무엇인가

원문에서 말하는 프론트엔드의 잃어버린 10년은 프론트엔드가 발전하지 않았다는 뜻이 아니다.

오히려 프론트엔드는 엄청나게 발전했다.

React, Vue, Svelte, Next.js, Vite, TypeScript 등 수많은 도구가 등장했고 개발 생산성도 높아졌다.

하지만 그 과정에서 일부 기본기가 가려졌다.

예를 들어 버튼을 만든다고 해보자.

```html
<button type="button">저장하기</button>
```

HTML의 기본 버튼을 사용하면 키보드 접근성, 포커스, 기본 동작 등을 브라우저가 자연스럽게 처리한다.

하지만 아래처럼 작성하는 경우도 있다.

```html
<div onclick="save()">저장하기</div>
```

화면상으로는 비슷해 보일 수 있다.

하지만 접근성, 키보드 조작, 의미 있는 HTML 측면에서는 큰 차이가 있다.

문제는 이런 차이를 모른 채 “동작하니까 괜찮다”고 생각하는 것이다.

이것이 프론트엔드 기본기가 가려지는 대표적인 예다.

## 5. AI 코딩도 비슷한 흐름을 만들고 있다

AI 코딩도 비슷한 탈숙련화를 만들 수 있다.

예전에는 개발자가 코드를 직접 작성하고 이해해야 했다.

이제는 AI에게 이렇게 요청할 수 있다.

> “로그인 폼 만들어줘.”
> 
> 
> “이 컴포넌트 리팩토링해줘.”
> 
> “Next.js에서 API 연결하는 코드 만들어줘.”
> 
> “Tailwind로 반응형 카드 UI 만들어줘.”
> 

AI는 빠르게 결과물을 만들어준다.

이 방식은 진입 장벽을 낮춘다.

초보자도 더 빠르게 결과물을 만들 수 있고, 숙련자도 반복 작업을 줄일 수 있다.

하지만 동시에 위험도 있다.

AI가 만든 코드가 항상 좋은 코드라는 보장은 없다.

AI가 만든 코드는 다음과 같은 문제를 가질 수 있다.

- 접근성이 부족할 수 있다.
- 성능상 비효율적일 수 있다.
- 보안상 위험할 수 있다.
- 프로젝트 구조와 맞지 않을 수 있다.
- 브라우저 기본 동작을 무시할 수 있다.
- 예외 처리가 부족할 수 있다.
- 유지보수하기 어려울 수 있다.

즉, AI가 코드를 생성해도 그 코드가 좋은 코드인지 판단하는 책임은 여전히 개발자에게 있다.

---

## 6. 높은 추상화는 편하지만, 결국 샌다

프레임워크와 AI의 공통점은 둘 다 높은 추상화라는 점이다.

프레임워크는 브라우저의 복잡성을 감춘다.

AI는 코드 작성의 복잡성을 감춘다.

높은 추상화는 편하다.

하지만 추상화가 감춘 세부사항이 완전히 사라지는 것은 아니다.

접근성, 성능, 브라우저 동작, 네트워크 환경 같은 문제는 언젠가 사용자 경험으로 드러난다.

예를 들어 무거운 클라이언트 사이드 JavaScript는 고성능 기기에서는 괜찮아 보일 수 있다.

하지만 저사양 기기나 느린 네트워크 환경에서는 사용자 경험을 크게 해칠 수 있다.

AI가 만든 코드도 마찬가지다.

처음에는 그럴듯하게 동작할 수 있다.

하지만 문제가 생기면 결국 사람이 코드를 읽고 원인을 이해해야 한다.

즉, 추상화는 편하지만 결국 샌다.

---

## 7. AI 코딩은 비결정적인 추상화다

일반적인 도구나 컴파일러는 비교적 결정적이다.

같은 입력을 넣으면 보통 같은 결과가 나온다.

하지만 AI 코딩은 다르다.

같은 요구사항을 입력해도 매번 다른 코드가 나올 수 있다.

모델이 바뀌면 결과도 바뀔 수 있다.

프롬프트 표현이 조금 달라져도 구현 방향이 달라질 수 있다.

그래서 원문은 AI 코딩을 일종의 **비결정적인 추상화**로 본다.

이 점이 중요하다.

AI는 단순한 컴파일러처럼 동작하지 않는다.

AI는 확률적으로 그럴듯한 코드를 생성한다.

그렇기 때문에 개발자는 AI가 만든 코드를 더 비판적으로 읽어야 한다.

---

## 8. LLM은 Stack Overflow 복붙의 연장선이다

원문에서 흥미로운 부분은 LLM 사용을 완전히 새로운 현상으로만 보지 않는다는 점이다.

예전에도 개발자는 Google과 Stack Overflow를 통해 빠르게 답을 찾았다.

문제는 검색해서 가져온 코드를 이해하지 않고 그대로 붙여 넣는 경우였다.

LLM도 비슷하다.

AI가 만들어준 코드는 빠르게 동작할 수 있다.

하지만 그 코드가 왜 동작하는지, 기존 코드베이스에 맞는지, 장기적으로 유지보수 가능한지는 사람이 판단해야 한다.

예전에는 Stack Overflow 답변을 읽고 이해한 뒤 사용해야 했다.

이제는 LLM이 만든 코드를 읽고 이해한 뒤 사용해야 한다.

도구가 바뀌었을 뿐, 핵심은 같다.

> 가져온 코드를 이해하지 못하면 결국 문제가 된다.
>

## 9. 중요한 것은 코드를 만드는 능력보다 판단하는 능력이다

AI 시대에는 단순히 코드를 빠르게 작성하는 능력의 가치는 줄어들 수 있다.

하지만 반대로 더 중요해지는 능력이 있다.

바로 **판단하는 능력**이다.

개발자는 이런 질문에 답할 수 있어야 한다.

- 이 HTML 구조가 의미적으로 맞는가?
- 이 UI는 키보드만으로 사용할 수 있는가?
- 이 CSS는 불필요하게 복잡하지 않은가?
- 이 컴포넌트는 과하게 렌더링되지 않는가?
- 이 상태는 클라이언트에 있어야 하는가, 서버에 있어야 하는가?
- 이 코드는 기존 코드베이스의 구조와 맞는가?
- 이 구현은 유지보수하기 쉬운가?
- 이 문제는 JavaScript로 해결해야 하는가, CSS로 해결할 수 있는가?
- 이 코드가 실제 사용자 경험에 어떤 영향을 주는가?

AI가 코드를 작성해줄 수는 있다.

하지만 이런 판단을 완전히 대신해주기는 어렵다.

결국 AI를 잘 쓰려면 개발자가 기본기를 알고 있어야 한다.

## 10. 프론트엔드 기본기가 중요한 이유

프론트엔드 기본기는 오래된 지식이 아니다.

오히려 AI 시대에 더 중요한 기준점이 된다.

### 10-1. HTML

HTML은 단순히 화면에 요소를 배치하는 문법이 아니다.

HTML은 문서의 구조와 의미를 표현한다.

의미 있는 HTML은 접근성, SEO, 유지보수성에 영향을 준다.

AI가 화면상으로는 동작하는 코드를 만들어도, 그 구조가 의미적으로 올바른지는 개발자가 판단해야 한다.

### 10-2. CSS

CSS는 단순히 예쁘게 꾸미는 도구가 아니다.

CSS는 레이아웃, 반응형, 상태 표현, 사용자 환경 대응까지 담당한다.

CSS를 잘 알면 불필요한 JavaScript를 줄일 수 있다.

예를 들어 다음과 같은 기능은 CSS만으로도 많은 부분을 해결할 수 있다.

- Flexbox
- Grid
- Container Query
- CSS 변수
- media query
- prefers-reduced-motion
- position sticky
- scroll behavior

AI가 JavaScript로 복잡하게 구현한 것을 CSS로 더 단순하게 해결할 수도 있다.

### 10-3. 브라우저

프론트엔드는 결국 브라우저 위에서 동작한다.

브라우저는 HTML을 파싱하고, CSS를 계산하고, JavaScript를 실행하고, 화면을 렌더링한다.

브라우저의 동작 방식을 이해하면 성능 문제를 더 잘 파악할 수 있다.

중요한 개념은 다음과 같다.

- 렌더링 과정
- Reflow
- Repaint
- 이벤트 루프
- 네트워크 요청
- 캐싱
- 이미지 로딩
- Core Web Vitals

AI가 만든 코드가 동작은 하더라도 렌더링 성능이 나쁠 수 있다.

이때 브라우저 지식이 있어야 병목을 찾고 개선할 수 있다.

### 10-4. 접근성

접근성은 선택 사항이 아니다.

좋은 프론트엔드 개발의 중요한 기준이다.

사용자는 모두 같은 방식으로 서비스를 사용하지 않는다.

어떤 사용자는 마우스 대신 키보드를 사용한다.

어떤 사용자는 스크린 리더를 사용한다.

어떤 사용자는 작은 화면이나 느린 네트워크 환경에서 서비스를 사용한다.

AI가 만든 UI가 겉으로 보기에는 멀쩡해도, 실제로는 접근성이 부족할 수 있다.

접근성을 고려하는 능력은 여전히 개발자에게 필요하다.

## 11. 품질은 정말 중요한가

원문은 여기서 현실적인 질문을 던진다.

개발자는 좋은 품질의 소프트웨어가 중요하다고 믿는다.

하지만 실제 비즈니스에서는 소프트웨어 품질과 성공이 항상 강하게 연결되지는 않는다.

느린 웹사이트도 잘 팔릴 수 있다.

접근성이 부족한 서비스도 시장에서 성공할 수 있다.

기술적으로 아쉬운 제품도 브랜드나 가격, 시장 상황 때문에 살아남을 수 있다.

이 말은 품질이 중요하지 않다는 뜻이 아니다.

오히려 현실에서는 품질이 항상 보상받지 못하기 때문에, 품질을 신경 쓰는 개발자의 역할이 더 중요하다는 뜻에 가깝다.

AI가 빠르게 코드를 만들수록 “일단 동작하는 코드”는 더 많아진다.

그럴수록 누군가는 계속 질문해야 한다.

> 이 코드는 정말 좋은 사용자 경험을 만드는가?
> 
> 
> 이 코드는 오래 유지보수할 수 있는가?
> 
> 이 코드는 모든 사용자에게 동작하는가?
>

## 12. Bauhaus 비유

원문 후반부에서는 Bauhaus를 예로 든다.

산업화 시대에 수공예 기술이 공장 생산으로 대체되었을 때, Bauhaus는 공장과 장인을 대립시키기보다 산업 생산 조건에 맞는 새로운 디자인 방식을 만들려고 했다.

중요한 것은 재료와 제작 방식을 이해하고, 최종 사용자를 계속 생각하는 것이었다.

이 비유를 소프트웨어에 적용하면 다음과 같다.

AI를 거부하는 것이 답은 아니다.

하지만 AI가 만든 결과물을 좋은 제품으로 만들려면 개발자는 여전히 재료를 알아야 한다.

웹 개발자에게 그 재료는 다음과 같다.

- HTML
- CSS
- JavaScript
- 브라우저
- 네트워크
- 접근성
- 성능
- 사용자 경험

산업 디자이너가 재료의 특성을 이해해야 하듯, 프론트엔드 개발자도 웹이라는 재료를 이해해야 한다.

---

## 13. AI를 쓰지 말자는 이야기는 아니다

이 글의 핵심은 AI를 쓰지 말자는 이야기가 아니다.

AI는 매우 유용한 도구다.

AI를 잘 사용하면 다음과 같은 도움을 받을 수 있다.

- 반복 작업 자동화
- 예제 코드 생성
- 리팩토링 아이디어 얻기
- 테스트 코드 초안 작성
- 문서 요약
- 낯선 기술의 진입 장벽 낮추기
- 빠른 프로토타입 제작

특히 MVP나 실험 단계에서는 AI가 큰 도움이 될 수 있다.

아직 제품-시장 적합성을 찾지 못한 상황에서는 빠르게 만들고 검증하는 것이 더 중요할 수 있다.

하지만 빠르게 만든 코드가 계속 유지될 코드라면 이야기가 달라진다.

언젠가는 다시 구조를 정리해야 하고, 성능을 봐야 하고, 접근성을 봐야 하고, 유지보수성을 봐야 한다.

AI는 도구일 뿐이다.

그 도구를 어디에 쓰고, 어디까지 믿고, 어디서부터 사람이 책임질지 판단하는 것은 개발자의 몫이다.

---

## 14. 프론트엔드 개발자는 앞으로 무엇을 공부해야 할까

AI 시대의 프론트엔드 개발자는 단순히 프레임워크 사용법만 공부해서는 부족하다.

React, Next.js, TypeScript 같은 기술은 여전히 중요하다.

하지만 그 아래에 있는 기본기도 함께 공부해야 한다.

중요한 기본기는 다음과 같다.

1. 의미 있는 HTML 작성하기
2. CSS 레이아웃과 반응형 제대로 이해하기
3. 브라우저 렌더링과 성능 이해하기
4. 접근성 기본 원칙 익히기
5. 네트워크와 캐싱 이해하기
6. 프레임워크가 해결해주는 문제와 해결하지 못하는 문제 구분하기
7. AI가 만든 코드를 비판적으로 리뷰하기
8. 사용자 경험 관점에서 구현을 판단하기

프레임워크는 계속 바뀔 수 있다.

하지만 브라우저, HTML, CSS, 접근성, 성능 같은 기본기는 프론트엔드 개발자가 계속 가져가야 할 기준이 된다.

---

## 15. 결론

AI는 프론트엔드 개발을 더 빠르게 만들어준다.

하지만 빠르게 만든 코드가 항상 좋은 코드는 아니다.

프론트엔드 개발에서 중요한 것은 단순히 화면을 구현하는 것이 아니다.

사용자가 실제로 잘 사용할 수 있는 인터페이스를 만드는 것이다.

그리고 그러기 위해서는 HTML, CSS, 브라우저, 접근성, 성능 같은 기본기가 필요하다.

AI 시대에는 코드 작성 능력만큼이나 코드를 읽고, 판단하고, 수정하고, 책임지는 능력이 중요해진다.

그래서 이렇게 정리할 수 있다.

> AI가 코드를 대신 써주는 시대일수록,
> 
> 
> 프론트엔드 개발자는 더 기본기를 알아야 한다.
> 

AI는 개발자를 대체하는 마법이 아니다.

AI는 개발자의 판단을 더 크게 증폭시키는 도구다.

기본기가 약하면 AI는 그 약점을 더 빠르게 드러낸다.

기본기가 탄탄하면 AI는 그 역량을 더 크게 확장한다.
