# 나는 왜 아키텍처를 고민하게 됐나 — 파일 하나에서 시작된 이야기

> 프론트엔드 아키텍처 시리즈 1편.
이 글은 답을 주지 않는다. **답을 찾기 전에, 내가 무엇 때문에 고민하게 됐는지**를 먼저 이야기한다. 도메인이니 FSD니 하는 단어를 꺼내기 전에, 그게 도대체 어떤 통증에 대한 답이었는지를 같이 겪어보고 싶다.
> 

프론트엔드 프로젝트는 예외 없이 `App`, `index`, `main` 같은 **파일 하나**에서 시작한다. 백엔드처럼 레이어 구조를 받아 들고 시작하는 게 아니다. 빈 캔버스를 받고, 우리가 스스로 구조를 만들어 나가야 한다.

그래서 우리는 코드가 불어날 때마다 본능적으로 손을 움직인다. 함수를 나누고, 파일을 나누고, 폴더로 묶고, 또 나눈다. 문제는 이 본능을 **이름도 기준도 없이** 휘두를 때 생긴다. 분명히 누구보다 열심히 나눴는데, 코드는 점점 더 못 찾고 못 고치는 물건이 되어 간다.

이 글은 그 과정을 단계별로 따라간다. 각 단계는 *누가 시켜서* 가 아니라 *아파서* 넘어간다. 마지막에 나는 어떤 막다른 벽 앞에 서게 되는데, 바로 그 벽이 내가 아키텍처를 공부하게 된 이유다.

---

## 0단계 — 시작은 항상 옳다

기능은 단순하다. 장바구니를 받아 가격을 계산하고, 할인을 적용하고, 결제하고, 완료 알림을 보내고, 영수증을 보여준다. 처음엔 이렇게 짠다. 그리고 **이건 잘못이 아니다.**

```tsx
// OrderPage.tsx
export default function OrderPage({ cart, user, couponCode }: Props) {
  const [receipt, setReceipt] = useState<Receipt | null>(null);
  const [loading, setLoading] = useState(false);

  async function handlePay() {
    setLoading(true);

    let subtotal = 0;
    for (const item of cart) subtotal += item.price * item.quantity;

    let discount = 0;
    if (user.grade === "vip") discount += subtotal * 0.1;
    else if (user.grade === "gold") discount += subtotal * 0.05;
    if (couponCode === "WELCOME") discount += 5000;

    const shipping = subtotal - discount >= 50000 ? 0 : 3000;
    const total = subtotal - discount + shipping;

    const { paymentId } = await (await fetch("/api/pay/card", {
      method: "POST", body: JSON.stringify({ amount: total, userId: user.id }),
    })).json();
    await fetch("/api/orders", { method: "POST", body: JSON.stringify({ paymentId, cart, total }) });
    await fetch("/api/notify/email", {
      method: "POST", body: JSON.stringify({ to: user.email, message: `결제 완료: ${total}원` }),
    });

    setReceipt({ subtotal, discount, shipping, total });
    setLoading(false);
  }

  return (
    <div>
      {/* ...장바구니 렌더링... */}
      <button onClick={handlePay} disabled={loading}>결제하기</button>
      {receipt && <ReceiptView receipt={receipt} />}
    </div>
  );
}
```

작은 프로젝트에서 이 코드는 **최선**이다. 한 화면 안에 다 있어서 읽기 쉽고, 파일을 점프할 필요도 없다. 여기서 "분리해야지!"라고 달려드는 게 오히려 과설계다. 문제는 코드가 **여기서 멈추지 않는다**는 것뿐이다

## 1단계 — 함수가 길어진다

*"할인 정책에 수량 할인이랑 기간 한정 쿠폰을 추가해 주세요."* `handlePay`가 부풀기 시작한다. 이제 이 함수를 읽는 동안 "지금 보는 게 계산인가 결제인가 알림인가"를 계속 머릿속으로 구분해야 한다.

그래서 **같은 파일 안에서** 이름 있는 함수로 떼어낸다. 가장 값싼 첫 분리다.

```tsx
function calcSubtotal(cart: CartItem[]) { /* ... */ }
function calcDiscount(subtotal: number, user: User, coupon: string) { /* ... */ }
```

`handlePay`가 다시 읽힌다. 흐름이 "소계 → 할인 → 결제 → 저장 → 알림"으로 한눈에 보인다.

## 2단계 — 파일이 끝나지 않는다

이번엔 `calcDiscount`를 **다른 화면에서도 쓰고 싶은데** `OrderPage.tsx` 안에 갇혀 있다. 게다가 파일은 이미 300줄을 넘겼다. 그래서 **파일을 분리**한다.

```
src/
├── OrderPage.tsx
├── price.ts
├── payment.ts
├── order.ts
└── notification.ts
```

화면은 가벼워지고, 로직은 어디서든 가져다 쓸 수 있게 됐다. 좋다. 그런데 이 "파일을 나눈다"가 습관이 되면서, 진짜 문제는 지금부터 시작된다.

## 3단계 — 파일 200개, 그리고 미아가 된다

기능이 늘면서 같은 패턴으로 파일이 계속 태어난다. `price.ts`, `payment.ts`, `validation.ts`, `useOrder.ts`, `orderApi.ts`… 예약, 매출, 회원, 결제마다 이런 파일이 줄줄이 생긴다. 어느 날 `src/` 아래 파일이 **200개를 넘긴다.** 전부 평평하게 한 바닥에 흩어진 채로.

그리고 깨닫는다. **파일이 5개였을 때보다 200개인 지금, 코드를 더 못 찾는다.**

분리는 했지만 **모으지 않았기** 때문이다. 그래서 자연스럽게 다음 손이 나간다 — 폴더로 묶자. 가장 직관적인 기준은 **역할**이다. 200개 파일을 20개 폴더로 정리한다.

```
src/
├── components/      # 모든 화면 컴포넌트
├── hooks/           # 모든 훅
├── api/             # 모든 API 호출
├── utils/           # 모든 계산 로직
├── constants/       # 모든 상수
├── types/           # 모든 타입
└── ...
```

흩어진 200개가 20개 폴더로 정돈됐다. 잠깐은, 정말 잠깐은 살 것 같다.

## 4단계 — presentation / container, 그리고 '얕고 넓은' 구조의 탄생

폴더로 묶고 나니 다른 게 눈에 거슬린다. 컴포넌트 하나에 화면 그리는 코드(UI)와 데이터 가져오고 가공하는 코드(로직)가 **여전히 섞여** 있다. 마침 좋은 패턴을 배운다. **Presentation / Container 패턴 — UI와 로직을 분리하라.**

그래서 화면을 둘로 가른다. 데이터를 다루는 컨테이너와, 그걸 받아 그리기만 하는 프레젠테이션으로.

```
src/
├── presentation/    # 순수하게 그리기만
├── containers/      # 데이터 가져오고 가공
├── hooks/
├── api/
├── constants/
├── types/
└── styles/
```

깔끔한 이론이다. UI와 로직이 깔끔하게 갈렸다. 그런데 이 결정이 우리를 어떤 구조로 데려가는지 보자. 폴더의 **종류**가 한 단계 더 늘었다. 모든 코드가 "무슨 역할인가"를 기준으로 가장 바깥에서 갈라진다. 깊이는 얕고, 폭은 넓다. 이게 **얕고 넓은 아키텍처**다.

이론적으로는 아름답다. 모든 게 제자리에 있다. 프레젠테이션은 프레젠테이션끼리, API는 API끼리. 그런데 실제로 코드를 만지기 시작하면, 한 번도 예상 못 한 통증이 찾아온다.

## 5단계 — 컴포넌트 하나를 알기 위해, 모든 폴더를 연다

*"주문 목록 화면 동작 좀 봐 주세요."* 라는 말을 듣고 `OrderList`를 파악하려 한다. 그런데 `OrderList`라는 한 가지를 이해하려면 이걸 다 열어야 한다.

!image.png

`presentation/OrderList.tsx`에서 화면을 보고, `containers/OrderListContainer.tsx`에서 데이터 흐름을 보고, `hooks/useOrderList.ts`를 거쳐, `api/orderApi.ts`를 확인하고, `constants/orderConstants.ts`를 찾고, `types/order.types.ts`를 뒤지고, `styles/orderList.styles.ts`까지 연다. **한 기능을 이해하려고 7개 폴더, 7개 파일을 횡단한다.**

3단계의 통증(파일이 흩어져 못 찾는다)을 분명히 해결하려고 폴더로 묶었는데, 묶는 기준이 "역할"이었던 탓에 **정작 함께 변하는 것들이 다시 사방으로 흩어졌다.** 주문 할인 정책 하나를 바꾸려 해도, 일곱 군데를 열어 일곱 군데를 고친다. 분리는 극대화됐는데, 한 기능의 응집은 바닥이다.

여기서 진짜 깨달음이 온다. **분리를 더 잘한다고 풀리는 문제가 아니었다.** 우리는 줄곧 "어떻게 더 잘 나눌까"만 고민해 왔는데, 정작 던졌어야 할 질문은 따로 있었다.

> **"무엇을 기준으로 묶을 것인가?"**
> 

하지만 이 질문에 곧장 "도메인으로 묶어라" 같은 정답으로 점프하지는 못했다. 사람은 익숙한 손부터 뻗는 법이고, 나도 그랬다. 그 시행착오가 사실은 이 글에서 가장 중요한 부분이다.

## 6단계 — 익숙한 손부터 뻗어본다, 그리고 부작용

### 시도 A — "그럼 presentation 안에서 기능별로 또 묶자"

가장 먼저 나온 손이다. 바깥의 역할 폴더는 그대로 두고, 그 **안을** 기능별로 한 겹 더 나눈다.

```jsx
presentation/
├── order/      └ OrderList.tsx
└── cart/
hooks/
├── order/      └ useOrderList.ts
└── cart/
api/
├── order/      └ orderApi.ts
└── cart/
```

한 시간쯤 뿌듯하다가 깨닫는다. **하나도 안 풀렸다.** `order`라는 개념은 여전히 `presentation/order`, `hooks/order`, `api/order`… 일곱 군데에 흩어져 있다. 횡단 거리는 그대로고, 폴더 깊이만 한 단계 더 깊어졌다. 오히려 나빠진 것도 있다 — 같은 이름의 `order/` 폴더가 일곱 번 복제됐고, 주문 도메인을 통째로 들어내려면 일곱 곳을 일일이 돌아야 한다.

여기서 첫 번째 깨달음. **가장 바깥 폴더(1차 분류 축)가 "역할"인 한, 그 안에서 무슨 짓을 해도 기능은 흩어진다.** 안에서 묶는 건 2차 축일 뿐이다. 진짜 문제는 1차 축에 있었다.

### 시도 B — "그럼 축을 뒤집자"

1차 축을 역할에서 **기능으로** 뒤집는다. 가장 바깥을 도메인으로 가른다.

!image.png

!image.png

```jsx
order/
├── OrderList.tsx
├── OrderListContainer.tsx
├── useOrderList.ts
├── orderApi.ts
└── order.types.ts
cart/
└── ...
```

드디어 함께 변하는 것이 함께 모인다. 주문을 고치려면 `order/` 하나만 열면 되고, 들어낼 때도 폴더째 지우면 끝이다. 횡단 지옥이 풀렸다. **그런데 바로 이 순간, 진짜 어려운 질문 세 개가 한꺼번에 날아든다.**

첫째, **`Button`, `Modal`, `Input` 같은 공통 UI는 어디 두지?** 얘넨 주문 것도 장바구니 것도 아니다. `order/`에 넣으면 `cart/`가 못 갖다 쓰고, 양쪽에 두면 중복이다. → 이때 처음으로 `shared/`가 왜 필요한지 몸으로 안다.

둘째, **도메인 경계가 애매한 코드는 누구 소유지?** 주문이면서 결제이기도 한 로직, 여러 곳이 같이 쓰는 계산. 경계를 어디에 그을지 매번 결정해야 한다. → "도메인을 어떻게 나누나"라는, 이 시리즈에서 가장 어려운 문제.

셋째, **`order/`가 `member/`를 import 하기 시작하면?** 도메인끼리 서로를 마구 참조하면, 폴더만 나눴지 실제로는 다시 한 덩어리다. → 단방향 의존성이라는 규칙이 왜 필요한지 여기서 나온다.

축을 뒤집는 건 횡단 문제를 풀었지만, 공짜가 아니었다. **공통의 위치, 경계 긋기, 의존 방향**이라는 세 개의 새 숙제를 안겨줬다.

사실 나는 이 "축 뒤집기"를 도메인이라는 말을 알기 한참 전에 이미 한 번 해본 적이 있다. WebRTC 기반 프로젝트에서 모듈이 `pub`(송신) / `sub`(수신)으로 나뉘어 있었다. 전형적인 역할 기준 분리였고, 기능 하나를 건드릴 때마다 pub과 sub을 오가야 했다. 어느 날 나는 이걸 `video` / `audio`로 갈아엎었다. 역할(보내느냐 받느냐)이 아니라, **하나의 대상(영상이냐 음성이냐)을 중심으로** 코드를 다시 모은 것이다.

결과는 분명했다. `video`와 `audio`가 서로를 신경 쓰지 않고 **독립적으로 변경 가능**해졌다. 영상 로직을 고쳐도 음성은 건드릴 일이 없었다. 그리고 둘이 공통으로 쓰던 연결·시그널링 코드는 자연스럽게 `webRTC`라는 공통 모듈로 남았다 — 지금 보면 그게 바로 `shared`였다. 의존 방향도 `video`·`audio` → `webRTC` 한 방향으로 깔끔했다.

그때 나는 "도메인"도 "단방향 의존성"도 몰랐다. 그냥 아파서 객체 중심으로 묶었을 뿐이다. 그런데 돌이켜보니 그게 정확히 위의 세 숙제 — 응집(독립 변경), 공통의 위치(`shared`), 의존 방향 — 에 대한 답이었다. **이름을 몰라도, 통증은 사람을 같은 자리로 데려간다.**

### 시도 C — "UI도 종류가 많은데, 종류로 나누면?"

여기서 또 하나 흔한 유혹이 온다. UI는 종류가 많다 — 페이지, 위젯, 순수 컴포넌트, 디자인 시스템 단위(atom/molecule)… 이걸 종류로 계층화하고 싶어진다.

그런데 함정이 있다. **"종류(kind)"는 "함께 변하는가"와 무관한 축이다.** `OrderList`를 위젯으로 부르든 페이지로 부르든, 그건 주문이 바뀔 때 같이 바뀐다. 종류로 나누면 분류가 주관적이라("이건 위젯이야 컴포넌트야?") 팀 내 논쟁만 늘고, 정작 응집은 안 생긴다. UI를 가르는 1차 기준은 종류가 아니라 **"이게 특정 도메인의 것이냐, 진짜 범용이냐"** 여야 했다. 종류 구분은 그 다음 문제다.

---

이 세 번의 시도 끝에, 나는 같은 벽 앞에 섰던 사람들이 남긴 이름들을 비로소 이해하게 됐다 — 도메인, `shared`, 단방향 의존성, 그리고 FSD(Feature-Sliced Design) 같은 아키텍처들. 이것들은 전부 시도 B가 떠안긴 그 세 숙제에 대한 **서로 다른 대답**이었다. 그제서야 그 단어들이 시험 범위가 아니라 **내 통증의 이름**이라는 걸 알았다.

## 7단계 — 폴더는 다 나눴는데, 도메인끼리 대화가 필요하다

도메인으로 축을 뒤집고 나니 응집도, 단방향도, `shared`도 제자리를 찾았다. 그런데 마지막 통증이 하나 남아 있었다. **도메인은 결국 서로 협력해야 한다.** 주문이 끝나면 결제 결과를 알아야 하고, 결제는 회원 등급을 참고해야 한다.

가장 쉬운 길은 `order`가 `payment`를 직접 `import` 하는 것이다. 그런데 그 순간, 애써 끊어놓은 게 다시 붙는다. 두 도메인이 서로의 내부를 알게 되고, 한쪽을 고치면 다른 쪽이 깨지고, 결국 폴더만 나뉜 한 덩어리로 돌아간다. 6단계에서 본 그 결합이, 이번엔 도메인 사이에서 되살아난다.

여기서 내가 한 건, 두 도메인 사이에 **인터페이스 하나를 끼우는** 것이었다. `order`는 `payment`의 구체 구현을 모른다. 둘 사이에 놓인 계약(데이터 통로)만 안다. `payment`가 내부를 어떻게 바꾸든, 그 계약만 지키면 `order`는 한 줄도 바뀌지 않는다. 직접 의존이 끊기고, 둘 다 "계약"이라는 중간 지점만 바라보게 된다.

> *[작은 의존 그림 자리: order → [계약] ← payment — 직접 의존이 계약을 향해 꺾이는 모습]*
> 

그때는 이게 무슨 패턴인지도 몰랐다. 나중에야 알았다 — **구체 구현을 숨기고 계약만 노출**하는 것, 이게 수많은 디자인 패턴이 공통으로 하는 일이라는 걸. 폴더를 나누는 일(분리·묶기·펼침)이 "코드를 어디에 둘까"의 문제였다면, 여기서부터는 **"모듈 사이에 무엇을 오가게 할까"** 라는 다른 층위의 문제가 시작된다. 그리고 그 층위를 다루는 언어가 바로 디자인 패턴이다.

이게 1편이 다다른 마지막 벽이자, 다음 편의 입구다.

## 그래서, 질문만 남았다

7단계까지 오면서 폴더는 다 나눴다. 함수도, 파일도, 폴더도, 도메인도, 도메인 사이의 계약까지. 그런데 손에 쥔 건 깔끔한 구조가 아니라, **답을 모르는 질문 한 무더기**였다.

지금 이 폴더 구조가 정답인지조차 모르겠다.
UI는 어디 두지? 기능 로직은 어디 두지? API 호출은 또 어디 두지?
API와 기능이 한데 엮이면 그건 누구 소속이지? 기능과 UI가 엉키면 그 경계는 누가 긋지?
"기능"으로 묶자고 했는데 — 그 기능이 곧 도메인인가? 그럼 도메인은 대체 뭐지?
여기서 말하는 비즈니스 로직은 뭐고, 그냥 로직과는 뭐가 다르지? 그건 또 어디에 둬야 하지?

질문은 꼬리를 물고 끝나지 않는다. 그런데 가만히 들여다보면, 이 모든 질문은 결국 하나로 모인다 — **무엇을, 어디에, 어떤 관계로 둘 것인가.**

나는 6년 동안 이 질문들에 매번 맨손으로 부딪혔다. 그러다 알게 됐다. 같은 질문 앞에서도, 그것을 부르는 이름과 판단의 기준을 가진 사람은 흔들리지 않는다는 걸. 그 이름과 기준의 묶음을 우리는 **아키텍처**라고 부른다. 내가 아키텍처를 공부하는 이유는 그게 전부다. 정답을 외우기 위해서가 아니라, 이 질문들 앞에서 **스스로 판단할 언어를 갖기 위해서.**

그래서 다음 편부터, 이 질문들을 하나씩 연다.

---

> 다음 편부터는 시도 B가 남긴 그 세 숙제 — **공통은 어디에, 경계는 어디에, 의존은 어느 방향으로** — 를 하나씩 푼다. "무엇을 기준으로 묶을 것인가"의 가장 강력한 대답인 **도메인**이 정확히 무엇이고, 무엇이 도메인 로직이고 무엇이 세부사항인지부터. `shared`의 정체와 단방향 의존성, 그리고 FSD 같은 기성 아키텍처가 같은 질문에 어떻게 답하는지도 이어서 다룬다.
